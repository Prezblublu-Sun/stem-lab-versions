## 复核一

下面是我基于网页呈现的架构、源码片段和它自述的蓝图要点做的审查。需要先说明两点局限：文件在 `contract/entries.py` 的 `check_tables` 处被截断，我看不到 `states.py` 的十七条规则、`registry`/`experiments` 的写入实现和 `tests/`；我也没有直接读 `docs/蓝图.md`，只能从网页转述反推需求。因此下面关于“规模”“并发”“迁移”的判断，凡涉及实现细节的都用条件句标注。

## 一句话结论

架构骨架是长期科研平台里少见的“把可复现性拆成可执行约束”的做法，尤其契约层、哈希链、每轮 provenance 这三件事做对了方向；验收代码的隔离设计也对，但它目前是设计不是代码，而长期平台最怕的恰恰是“验证器本身没人验证”。主要风险不在设计错，在**规模上限、演进腐烂、运维闭环、多用户缺失**这四处。

---

## 一、架构设计：站得住的部分

**1. 契约层沉底、纯函数、碰盘集中。**
`contract/` 只用标准库、不 import 别的层，碰盘只在 `hashing`/`formats` 明确的几个函数。这意味着“读任何历史数据”的代码可以独立于核心和插件长期稳定——这是长期平台最关键的一条。很多平台死在“读旧数据的逻辑散落在业务代码里，业务一改旧数据就读不出”。

**2. 只追加哈希链的细节经得起推敲。**
`split` 返回末尾半行的字节数、append 前截掉，处理了崩溃写残行；`extends` 用备份时的链头查尾部整条删除（链自身查不出的盲区）；`link` 拒绝 `body` 自带 `seq/prev/this`；`_no_constant` 拒绝 JSON 里的 `NaN/Infinity`；`check_chain` 先比对规范字节再比对哈希，能区分“被手改”和“换行/编码被改写”。这些不是教科书式的链，是按真实事故补过的链。

**3. 每轮 provenance 的颗粒度是对的。**
`ROUND_PROVENANCE` 里有 `commit`、`clean`、`frozen`、`plugin_hash`、`plugin_frozen`、`plugin_dirty`、`contract`、`python`、`lock`、`host`，再加 `PROVENANCE_SOURCES` 的 `remote/package/code/plugin` 后补。特别是两处：
- `plugin_dirty` 允许脏代码跑，但差异存 `plugin-<hash12>.diff`——比“脏了不许跑”（挡死科研）和“脏了不管”（毁掉复现）都务实；
- `code` 来源记录“这一轮中途插件代码变了”，这是长跑实验的真实场景，很多平台栽在这。

**4. `created` 抄入输入表/产物表/结局表。**
插件升级或拔掉后旧实验仍读得懂。配合 `versions.py` 的格式版本，这是“向前兼容”的正解。长期平台里插件一定会死、会重写，抄表是唯一低成本的解法。

**5. 依赖方向单一 + FROZEN 清单。**
四层单向、`tests` 和 `contract/registry/experiments/hooks/desk/core` 进冻结清单（174 个文件），自由部分（插件、board、界面、文档）可整体重写。这个“哪些能动、哪些不能动”的边界，是长期演进的前提。

## 二、架构设计：长期尺度下的风险

按严重程度排。

**（高）规模上限没有护栏。**
- 单实验单 `jsonl`，`view.view()` 每次从头折叠全部条目算现状。实验跑几百轮、每轮几十任务、十二种条目，单文件上千行；实验数上万时，`board.experiments.cards()` 虽按 `mtime` 缓存，首次和每次变化仍要重读全部实验。
- `check_chain` 是全量 O(n)，若备份时全量核对，规模上来会成为瓶颈（若 append 时只读尾部则 append 本身没问题，但核对仍是全量）。
- 建议：给单实验记录设归档阈值（比如 N 轮后写一份 `snapshot` 条目做检查点，折叠从快照起算），board 加一层“实验 id → 卡片”的持久索引；`check_chain` 平时增量、备份时全量。

**（高）并发写没有看到锁。**
`contract` 不碰盘是对的，但写入路径（`registry`/`experiments` 的 append）在截断之外。多用户或多进程同时向同一实验记录 append 时，`split` 的半行处理救不了“两条完整行交错”。长期共享平台必须回答：同一实验是否允许多写者？如果不允许，锁在哪、锁失效怎么恢复？

**（中高）多用户维度整体缺失。**
链里记了 `host` 但没记 `user`；`layout` 有 `is_experiment_id/item_id/key/label` 但没有所有者/可见性/操作权。如果平台是“一个 lab 共用”，这是硬缺口：出事时追不到人，隐私/竞争实验分不开。即便现在是单人，`user` 字段也应尽早进 `COMMON` 或 provenance，后补代价高。

**（中高）迁移测试是最容易腐烂的地方。**
`versions.py` + `FORMATS` 的“旧版本转新形状”是长期平台的生命线，但网页没展示迁移测试策略。建议：每个历史格式版本保留一份 golden 样本，迁移测试进 CI；迁移逻辑只增不改，旧迁移函数永久保留。

**（中）运维闭环不完整。**
`alerts` 只显示不动作是对的（避免误杀），但：
- 告警没有送达渠道（邮件/IM/webhook），无人值守时“网页上显示”等于没有；
- `last_backup` 只读备份时间，没看到自动备份机制；备份过期告警依赖外部有人真在备份；
- 求解槽在 `%TEMP%\stemlab-slots`，系统清理临时目录会误伤正在跑的槽，槽的生命周期（谁创建、谁回收、泄漏怎么清）需要显式定义。

**（中）`FROZEN` 是静态白名单。**
174 个文件靠人工维护，重构移动文件或新增文件忘了加就会失真。虽然 `tests` 里应有检查，但更稳的是“从目录推导 + 内容哈希”而非逐文件白名单；`frozen.trees` 已经是目录级，方向对，建议彻底目录化。

**（中）“悄悄失效”是显式 category，但默认策略要 fail-loud。**
把 silent 做成 outcome 的一种而非隐式吞掉，是对的——可查询、可审计。但平台层面应默认“出现 silent 即提升告警”，并且验收代码要有专门试验确保 silent 永远不会被下游当成 pass 消费。科研数据可信度的头号杀手就是“实验显示成功、结果是坏的”。

**（低）数据生命周期。**
产物用 `item + hash` 引用，但没有引用计数/GC/归档策略的展示。长期平台数据会膨胀，需要回答“哪些产物还被谁引用、哪些可删、删了链怎么记”。

## 三、验收代码：设计上的亮点

**1. 隔离四件套。**
被验系统从目标提交克隆、另用 `STEMLAB_DATA`、另用远端作业目录、只共用求解槽。这个组合很聪明：不污染真实账、不额外占机器、又能测到“和真实系统同机共存”的场景。

**2. `port.py` 单接口 + 插件内部一律不碰。**
验证代码只经固定接口（动作、记录产物、三张表和格式），插件实现怎么变都不影响验证。这让验收代码可以针对稳定契约写，寿命远长于插件。

**3. 三道保险对应可复现三要素。**
① 跑前对照（冻结清单没变）→ 环境固定；② 拼出写全的输入（不让插件在运行时悄悄补默认值）→ 输入明确；③ 跑后核对 → 结果可验。这个映射是清醒的。

**4. A/B/C 分级 + 31 项试验 + “提交过的才用”。**
分级避免“非黑即白”导致验证器被绕过；“提交过的才用”防止临时改验证器让测试变绿——这两条都是被现实教育过的设计。

## 四、验收代码：风险

**（最高）没写就是零，且要警惕“先写全再跑”。**
建议先写最小闭环：`port.py` + 跑前对照 + 一条端到端试验（新建→填→冻→跑→收→核对），跑通再铺 31 项。设计越完整，越容易在写第一行前反复改设计。

**（最高）验证器本身没有验证（meta-verification）。**
这是长期平台的经典陷阱。至少要有：
- **反向测试**：对着已知被破坏的 commit（删一条 provenance、改一个 output hash、让 plugin_dirty 不记 diff），验证器必须红；
- **验证器版本矩阵**：验证器依赖新接口就验不了旧 commit，需要“验证器版本 × 被验系统版本”的兼容矩阵，否则“考古式复现”会断。

**（高）共享求解槽是隔离的漏洞。**
共用 `%TEMP%\stemlab-slots` 意味着：
- 验证与被验系统同时跑时槽竞争，可能让“槽泄漏”类 bug 被掩盖或放大；
- 若求解器写共享状态（许可证、缓存目录），隔离不彻底。
建议：验证支持显式 `STEMLAB_SLOTS` 覆盖，并单列一项“槽泄漏”试验；共享槽只作为“共存场景”的补充，不作默认。

**（中高）覆盖矩阵要显式化。**
8 种实验类型 × 16 种种类 × 17 条状态规则 × 12 种条目 × 4 个插件接口，31 项试验是否覆盖每条规则，需要一张“规则 → 试验”的表进 CI，而不是靠叙述。否则规则加了、试验没加，没人发现。

**（中）快照会腐烂。**
网页提到“快照”。要区分两类：契约快照（应永不变，变了就是 bug）和输出快照（会随合理演进变）。后者若“一键更新快照”，很快会变成“点一下就绿”。建议输出快照带来源 commit + 手动批准记录。

**（中）`plugin_dirty` 的 diff 基线要钉死。**
`code` provenance 记了 `commit` 和 `plugin_dirty`，但 diff 的基线如果是 `git HEAD`，而 HEAD 在长跑中又变了，diff 会失配。需要明确“diff 相对哪个 commit”，并把基线 commit 一并记入。

## 五、从蓝图/长期平台视角的缺口清单

| 缺口 | 为什么长期会疼 | 建议 |
|---|---|---|
| 无 `user` 字段/权限 | 多人共用追不到人、实验分不开 | 尽早进 provenance 和 layout |
| 告警无送达 | 无人值守等于没有 | webhook/邮件 + 升级策略 |
| 无自动备份/异地链头 | 链能防篡改但防不了丢盘 | 定时备份 + 链头异地 |
| 数据无 GC/归档 | 几年后磁盘爆 | 引用计数 + 归档条目 |
| 槽生命周期不明 | 临时目录被清误伤 | 显式 root + 回收 |
| 验证器无反向测试 | 验证器自己腐烂 | mutation 测试进 CI |
| 迁移无 golden 样本 | 旧数据读不出 | 每版本一份样本 + 迁移测试 |

## 六、如果只做五件事（优先级）

1. **先把 `port.py` + 跑前对照 + 一条端到端试验写出来**，跑通再扩 31 项。
2. **反向测试**：对 5 个故意破坏的 commit，验证器必须红——这是验证代码可信度的地基。
3. **覆盖矩阵进 CI**：17 条状态规则、12 种条目、4 个插件接口，每条至少一项试验。
4. **自动备份 + 链头异地 + 告警送达**：链防篡改，但防不了丢盘和无人看。
5. **规模护栏**：单实验记录设归档阈值 + 快照检查点；board 加持久索引；`check_chain` 增量 + 备份全量。

## 七、我看到的局限

- 文件在 `entries.check_tables` 处截断，`states.py` 的 17 条规则、`registry`/`experiments` 的 append/锁实现、`tests/` 内容都看不到，关于并发和规模上限的判断需要对照实现复核。
- 没读 `docs/蓝图.md` 原文，“参考蓝图”部分只能从网页转述反推；若蓝图对多用户、数据归档有明确要求而网页没体现，我的缺口清单需要相应调整。
- “快照”“适配表”“31 项试验”的具体内容只在总览页一句话带过，覆盖充分性无法逐项核对。

整体判断：**这是一份思路清醒、细节经得起推敲的设计，后端的可复现性三要素（环境/输入/结果）落地得比多数科研平台扎实；它现在最大的敌人不是设计对手，是“验证代码还没写”和“规模/多用户/运维闭环还没回答”。**

## 复核二

# **stem-lab 1.0 架构与验收设计审查报告**

**审查基准：**《stem-lab 1.0 蓝图》（2026-11-13）\
**审查对象：**《stem-lab 架构与验证代码》HTML 中的架构、嵌入源码、测试目录及测试元数据\
\*\*评价视角：\*\*面向长期运行、反复迭代、跨机器协作的计算科研任务平台

## **一、总体判断**

我的总体判断是：

**stem-lab 1.0 的核心架构方向值得保留，但目前还不能把它视为已经完成工程验收、能够长期可信运行的科研平台。**

其主要优点并不在于采用了多少技术组件，而在于明确建立了几项非常重要的科研基础设施原则：

- **科研结果具有身份。** 骨模型、设计点、计算数据、预测器、策略和代码包，都有稳定编号、版本和内容哈希。
- **实验过程具有历史。** 实验、轮次、任务和产物分开建模，历史不是被新一轮计算覆盖。
- **状态可以重建。** 通过追加记录和状态折叠函数生成现状，而不是维护多套容易互相矛盾的状态表。
- **算法与实验管理分离。** FEA、重建、代理、优化可以迭代，而已经登记的科研结果原则上不应因插件升级而改变含义。
- **验证被纳入架构。** 不是先开发功能、最后补测试，而是从契约、边界、故障、跨机器和科学正确性几个方向规划验收。

这些原则对于持续数年的材料科学、计算力学和数据驱动优化研究尤其有价值。

但长期科研平台的最终要求不是“能够运行一次完整流程”，而是：

**在代码迭代、任务中断、机器更换、环境升级、数据规模增长甚至人员交接之后，仍然能够解释、验证、恢复和必要时复现历史科研结果。**

这将是以下审查中所有问题的判断标准。

### **审查证据的边界**

网页的数据中包含约 251 个文件条目、117 个可提取的 Python 实现文件，以及数百项测试函数元数据。它能够支持实际源码层面的静态审查，并非只能评价架构图。

不过，网页没有提供大多数 `tests/` 测试文件的完整正文，而是提供了函数名称、签名、位置和说明。因此，需要严格区分三种结论：

1. **源码确认的问题：** 能在嵌入的具体实现中定位。
2. **设计与验收缺口：** 蓝图有要求，但现有材料不能证明其已经满足。
3. **长期演进建议：** 即使当前实现符合蓝图，仍然建议补强的非功能性能力。

本报告不会将“存在测试文件”直接等同于“测试实际执行并通过”，也不会将尚未完成的科学验证判断为已通过。

## **二、审查结论与风险分级**

## **当前需要优先处理的问题**

暂不建议通过正式验收

| 等级 | 问题                              | 影响                |
| -- | ------------------------------- | ----------------- |
| P0 | 任务完成后仍允许被改回运行状态                 | 任务结果和重试语义不可靠      |
| P0 | 同一轮允许代码变化，但任务没有独立代码版本身份         | 科研结果无法精确归属到实际运行代码 |
| P0 | 计划中的验证任务使用共享账本，恢复时仅凭实验类型和备注寻找记录 | 跨版本验收可能错误复用旧实验    |
| P1 | 备份默认不逐文件核对内容哈希                  | 备份成功不代表科研产物字节正确   |
| P1 | 进程启动与状态持久化之间仍存在无法认领的作业窗口        | 中断后可能产生孤儿计算进程     |
| P1 | 验证代码第二版尚未实现，跨机器和科学测试不属于默认检查     | 目前缺少正式验收证据        |
| P1 | 插件运行在具有数据写入权限的核心进程中             | 插件的隔离边界主要靠约定      |
| P2 | 历史记录重放、文件哈希与冻结代码规模存在增长压力        | 多年运行后可维护性和性能下降    |

这里的等级定义为：**P0** 应在正式科研使用或有效性验收前修复；**P1** 应在长期无人值守和跨机器使用前完成；**P2** 可以阶段性实施，但应提前保留演进接口。

另有一个直接的版本状态问题：HTML 记录的工作区中，`FROZEN`、部分契约源码及固定测试标记为 `modified`。而 `stemlab/desk/core/start.py:116–129` 明确要求固定文件符合清单、契约与核心没有未提交改动。因此，网页展示的这个工作区状态不能直接视为可发布的干净版本。正式验证应针对明确的 Git 提交，而不是这一份混有未提交改动的工作区快照。

## **三、架构设计评价：哪些应当保留**

### **3.1 四层架构及八个实验类型是合理的**

蓝图中的核心依赖方向可概括为：

**展示层** — `desk/ui`、`board`

交互、查询、可视化、告警

操作与执行协调层

`desk/core`

`hooks`

`registry`

`experiments`

**契约层** — `contract`

格式、身份、哈希、状态、接口

**科研插件** — `recon` / `fea` / `surrogate` / `opt`

通过 hooks 接入；提供计算实现

箭头代表模块依赖方向，插件通过 hooks 获得能力，而不是直接拥有账本写入接口。

我支持这种分层，不建议为了引入大型任务编排框架、微服务或者分布式数据库而推翻它。

长期计算科研平台真正需要稳定的是实验身份、数据格式、执行记录和历史解释能力，而不是具体的算法实现。当前设计已经抓住了这一点。

尤其值得保留的是每个实验类型在 `created` 记录中保存自己的输入表、产物表和结局表。即便以后重写或删除插件，历史实验仍然具备基本的解释结构。这是一个很好的长期兼容性设计。

### **3.2 不可变登记与事件记录优于直接维护一张可修改状态表**

`register.jsonl` 与实验 `record.jsonl` 的思路是合理的。

它具有三个优点：

- 审计与状态计算基于同一原始记录。
- 失败、重试和人工干预不会覆盖历史。
- 使用 SHA-256 链可以发现中间条目被修改或删除。

`contract/states.py` 使用统一的规则表，并通过 `fold()` 计算状态，也符合蓝图强调的“规则只有一份”。

不过，这种结构应定义为**可验证的追加日志**，而不是绝对不可篡改的账本。文件权限和只读属性不能防止拥有相应操作系统权限的进程修改文件；哈希链主要负责发现篡改，备份及独立校验点负责恢复和检测尾部截断。

因此，设计原则应当保留，但实现必须补齐下面讨论的状态转移和持久化一致性约束。

### **3.3 八个实验类型对科研闭环的划分正确**

从 `recon.draft`、`recon.finalize`，到 `fea.run`、`surrogate.train`、`surrogate.predict`、`surrogate.check`，再到 `opt.pool` 和 `opt.select`，这套类型体系覆盖了计算科研的重要阶段。

我特别认可三项安排：

**首先，人工检查没有被伪装成自动化成功。** 重建候选与定稿分成两个实验，人工修改需要登记。这样既支持自动计算，也保留专家审核的责任边界。

**其次，FEA 中区分计算结论与计算异常。** “放不进去”可以构成科学结论，但“不收敛”“网格失败”先列入待查。这样能避免优化算法把数值求解失败错误地学习成物理不可行。

**最后，代理训练与代理复核分离。** 预测器训练完成不代表其推荐的方案可信。后续通过真实 FEA 对预测进行独立复核，是闭环优化中必须保留的步骤。

从科学方法论看，这种设计已经超过普通工作流调度器，具备建设科研证据链的基础。

## **四、源码层面的关键问题**

以下结论主要基于 HTML 内嵌的 Python 源码，而不是仅根据架构说明推断。

### **4.1 P0：任务状态转换没有形成真正的状态机**

已确认的实现缺陷

`stemlab/contract/states.py:200–204, 372–381`

蓝图规定了任务的五种状态，并通过任务结局区分成功、科学结论、可重试失败和待查失败。这一设计本身正确。

但当前 `_task_ok()` 主要验证两件事：任务属于当前轮次，以及所填结局名称与状态是否匹配。它没有完整验证**已有任务状态能否转换到新状态**。

而 `_task()` 会直接用新记录覆盖当前任务状态。

这意味着已经记录为 `done` 的任务，仍可能被下一条 `running` 记录改回运行中。我通过调用提取出的状态契约代码确认了这一行为。

这不是显示问题，而会直接影响：

- 已完成 FEA 任务是否被错误重新计算。
- 任务完成的科学结论是否在状态重放中消失。
- 重试逻辑是否将已经完成的任务重新排队。
- 断点恢复是否依赖任务消息到达顺序。

**修改建议：** 在契约层引入独立的任务状态转移表，而不是仅校验任务状态与结局类别。

建议将任务分成两个维度：`task_id` 代表科学任务身份，`attempt_id` 代表某一次执行尝试。同一轮次内，终态不应被直接撤销；如果需要重试，必须创建新的尝试或明确的新轮次。对于同一次尝试，任务指纹、输入及执行代码身份也必须保持稳定。

最低验收条件是：任务一旦成功，后续迟到的 `queued`、`running` 或 `failed` 消息均不能改变已经确认的成功结果。

### **4.2 P0：代码可变性与科研结果身份存在冲突**

已确认的溯源缺口

`desk/core/start.py:133–154`；`plugins/fea/jobs.py:56–65`

当前设计允许一轮实验运行过程中自由插件代码发生变化，并通过追加 `provenance` 记录变更信息。

这是灵活的开发机制，却与蓝图中的一项关键假设发生冲突：**只凭数据行的轮号就能找到计算该行时实际使用的代码。**

假设同一轮 FEA 中发生以下过程：

第 3 轮

同一实验、同一轮次

任务 A

插件代码 v1

完成

代码修改

插件代码 v2

已记录变更

任务 B

插件代码 v2

完成

如果数据行只写 `round=3`，无法独立确定任务 A 与 B 实际使用的是哪一版自由代码。

除此之外，`plugins/fea/jobs.py` 的输入指纹由点、骨模型、内核、导出设定和插件冻结文件构成。这与蓝图列出的五个组成部分一致，但**没有覆盖可能改变计算结果的全部实际依赖**，尤其包括：

- 自由插件代码的实际版本。
- `derive_def` 推导量定义的版本。
- 实际调用的求解器及其版本。
- 可能影响数值结果的执行环境。

因此，这不是单纯的“蓝图没实现好”，而是**蓝图中科研计算身份的定义还需要增强**。

建议保留已有 `input_fingerprint`，再引入独立的 `execution_fingerprint` 或 `execution_manifest_hash`。后者包含任务真正执行时使用的代码、依赖和环境，并记录在每一个执行尝试中。

更稳妥的运行策略是：**轮次开始时固定该轮的可执行代码快照。** 如果研究者修改算法，可以继续开发，但已经运行的轮次不立即采用修改；要启用新版代码，就创建新轮次或新的执行身份。

对于科研平台，我更推荐这种方式，而不是允许一轮内部发生未经任务级精确绑定的代码热切换。

### **4.3 P1：产物发布具有恢复设计，但恢复路径仍需强化验证**

`stemlab/hooks/publish.py:121–150`

蓝图中的六步产物发布流程是值得保留的设计：核对清单、移动、计算哈希、只读、登记、追加 `output`。它明确考虑了步骤之间发生崩溃的情况。

但 `_resume()` 在发现产物目录已经存在时，可以直接计算目录哈希并完成登记，没有明确重新执行正常路径中的全部格式适配检查。如果产物在第一次核验之后、最终登记之前发生变化，就存在恢复路径与正常发布路径使用不同验收标准的风险。

另外，已有登记项时，也需要明确验证实际文件内容是否仍与登记的哈希一致，而不是仅靠“该产物已登记”推断恢复成功。

建议把产物发布设计成严格的状态机：

候选已核验 → 内容已固定 → 已登记 → 已记入实验 → 可读取

所有恢复入口都应重新确认每个阶段的不变量。产物应在成为“可读取的正式结果”之前完成完整检查，避免下游消费者看到半发布状态。

这部分还需要特别测试：在每个持久化边界注入崩溃，重启对账后必须得到唯一、完整、哈希一致的产物记录，不能多登记、漏登记或接受内容变更。

### **4.4 P1：长时间运行的计算作业存在进程身份恢复窗口**

`plugins/fea/run.py:146–154, 236–245`

当前 FEA 执行器采用独立进程，运行前会先持久化启动意图，这是合理方向。

但外部进程创建与其 PID 等执行信息可靠持久化之间，不可能仅靠两个顺序操作消除全部崩溃窗口。如果核心在子进程启动成功后、保存完整身份前崩溃，恢复程序可能无法准确辨认已有进程。

对于几秒钟的小任务，后果可能不明显；对于持续数小时的求解，可能出现重复计算、孤儿进程或求解槽占用异常。

建议引入持久化的 `job_id` 和 `attempt_id`、进程启动确认协议，以及基于 PID、进程创建时间和唯一执行标识的恢复机制。同时，计算槽的所有权应绑定具体轮次与尝试，而不仅是任务名称。

特别需要区分三种状态：**核心失联、工作进程仍然存活、工作进程已确认失败**。不能将前两种自动折叠成第三种。

### **4.5 P1：备份过程偏重增量传输，缺少足够强的内容完整性证明**

`desk/core/backup.py:106–159`；`desk/core/check.py:89–140`

`backup.py` 的文件清单主要通过文件路径和长度判断需要传输哪些内容。默认备份验证没有对所有科研产物执行逐字节内容哈希核查。

因此，**两份内容已经不同、但文件大小完全相同的文件，可能无法通过默认增量判断发现问题**。

对长期科研任务而言，备份至少应提供两种证明：

一是**结构完整性**：实验链、登记链、发布记录与备份校验点相匹配。

二是**内容完整性**：产物文件的每个内容哈希与原始登记一致，恢复到新机器后依然一致。

还应定期进行真正的独立恢复演练，而不是只执行备份命令。一个多年积累的项目，备份文件存在不等于恢复路径可用。

建议将“最近一次可验证备份时间”“最近一次完整恢复演练时间”“未完成备份的新增数据量”纳入仪表盘。

### **4.6 P2：追加日志的重放成本将随任务规模显著增长**

`stemlab/experiments/log.py:32–50`

目前每次追加实验记录，都需要读取已有记录并执行状态重放。对于拥有大量 FEA 点、频繁任务状态变化、跨越多个轮次的实验，这会逐步演化为性能问题。

如果日志增长到 \\(N\\) 条，而每次追加都重放此前记录，总体工作量可能接近 \\(O(N^2)\\)。

我不建议因此立刻引入 PostgreSQL 或分布式数据库。可以继续坚持蓝图的三类权威存储，同时增加**可丢弃、可重建的索引和状态检查点**：

检查点必须绑定已验证的日志头哈希，不能成为第二套可独立修改的事实来源。如果检查点损坏，应能从原始日志重建。

这既保留了架构的简洁性，也能支持将来规模扩大。

## **五、验收代码设计：思路很好，但第二版尚未形成可信的执行闭环**

这部分需要单独评价。

网页中的“验证代码第二版”明确标记为**设计中、尚未编写**，主要以拟建目录、接口、设计方案和代码骨架呈现。因而，不能据此认定新的科学验收程序已经完成，更不能说其中的 31 个验证项目已通过。

### **5.1 我认可它的验证框架**

它不只是简单增加更多 `pytest`，而是在建立一套独立的科学验证体系。

① 运行前核对（Preflight）

核对代码版本、输入列、单位、物理含义、适配器、参照样本及验证协议

② 输入确定（Inputs）

固定试验设计、显式设定、完整条件和输入身份，避免隐含默认值

③ 真实运行（Runner）

通过真实操作台创建实验、启动计算、轮询、恢复及记录产物

④ 结果回读（Readback）

验证实际任务、实际参数、执行来历、输出内容和结果完整性

⑤ 独立科学分析与报告

与基准解、参照数据及预注册判据比较，保留统计证据和版本差异

特别值得肯定的是，验收设计意识到了一个科学计算系统常见的严重问题：

**“配置文件里写了某个参数”并不能证明求解器实际使用了该参数。**

网页为参数设置 A、B、C 三类验证等级：A 类可从实际产物回读，B 类依赖程序回写，C 类只能使用运行前探针间接验证。

这个方向正确，建议继续采用，并且将参数可观察性直接纳入科学结果的可信等级。

### **5.2 第二版代码骨架中需要修改的四个问题**

#### **第一：验证活动的身份不够唯一**

`validation/harness/port.py` 的规划代码中，`find_experiment()` 根据实验类型、备注和 `validation` 标签恢复实验；`runner.py` 生成的备注形如“协议编号 + 第几行”。

但不同验证活动可能重复执行相同协议和行号。如果多个活动共用同一份 `STEMLAB_DATA`，后一个活动就可能错误找到前一个活动创建的实验。

这对跨版本对照尤其危险：表面上是在验证新提交，实际却可能读取旧版本运行过的实验。

应将验证身份定义为：

\\[ \mathrm{RunKey}=H(\mathrm{CampaignID},\mathrm{ProtocolID},\mathrm{RowID},\mathrm{AttemptID}) \\]

每次验证活动应具有独立账本目录；共享的只能是受哈希约束的不可变缓存。恢复必须依赖唯一运行标识，而不是用备注文本模糊寻找。

#### **第二：长任务“无新记录”不能等同于“无进展”**

计划中的 `runner.wait()` 用实验记录条数是否增加来判断进展，并配置 `quiet_s` 超时。

然而，有限元求解器可能正常计算数小时却不产生新的实验事件。这样的任务会被错误判为无进展。

正确的健康监测应至少区分：核心是否存活、工作进程是否存活、求解器是否有心跳，以及是否真正超过科学上允许的执行时间。

此外，规划的超时异常路径需要在 `finally` 或等价的恢复流程中确认停止和资源清理，否则会留下仍在运行的验证作业。

#### **第三：**`readback`**&#x20;还不足以证明任务完整性**

在 `validation/harness/readback.py` 的代码草案里，主要遍历已有任务，比较其结局是否与期望一致。

但是，仅验证**实际存在的任务**是不够的。

例如，理论上应该执行 100 个 FEA 点，最终只创建了 97 个任务。如果其中 97 个任务都成功，单纯遍历已有任务可能错误通过。

必须改成集合级校验：

\\[ T\_{\mathrm{expected}}=T\_{\mathrm{actual}} \\]

再检查每个任务的终态、指纹、执行身份、产物行数、唯一性和对应关系。

如果某实验类型声明必须产出报告或预测器，也必须检查**必需产物存在且内容有效**，而不只是“存在时进行检查”。

#### **第四：数值容差不能统一设成一个极小常数**

代码草案中的 `same()` 默认使用 `rel_tol=1e-9` 和 `abs_tol=1e-12`。

这适合部分精确配置参数，但不适合作为所有计算科研结果的统一比较标准。

不同对象应采用不同判据：

| 比较对象           | 建议方法               |
| -------------- | ------------------ |
| 哈希、任务 ID、枚举、版本 | 严格相等               |
| 输入参数、单位、坐标系    | 精确比较或声明过的转换规则      |
| FEA 位移、应力、接触量  | 参考值误差、网格收敛及预定义物理容差 |
| GPU 代理预测       | 数值误差、重复运行方差和统计置信区间 |
| 优化算法效果         | 预算一致的重复实验和效果分布     |
| 回归测试           | 按输出变量制定容差并记录合理性依据  |

尤其不能以“GPU 模型包字节不一致”直接推断科学不可复现。对于随机算法，必须区分执行环境的可追溯性、数值可重复性和统计可重复性。

## **六、从材料科学与计算力学角度，还必须补强三项能力**

### **6.1 科学验证应区分软件正确、数值正确和物理可信**

建议将最终验收明确拆成三层。

| 层次       | 核心问题             | 典型验收证据                     |
| -------- | ---------------- | -------------------------- |
| **软件验证** | 程序是否按定义工作？       | 状态转移、异常注入、跨系统哈希、任务恢复、产物一致性 |
| **数值验证** | 数值方法是否正确求解所设方程？  | 解析解对照、网格收敛、平衡残差、求解器容差      |
| **物理确认** | 模型是否足够真实地代表研究对象？ | 实验测量、参照模型、材料参数敏感性、独立样本验证   |

举例来说，FEA 任务完成并返回一组应力值，最多证明任务执行产生了输出，不能证明有限元数值正确，更不能证明这些应力值代表实际骨组织行为。

对于股骨重建、接触分析和设计优化，材料分布、边界条件、几何误差及接触算法可能比求解器本身对结果影响更大。因此，科学验收需要独立于插件成功状态。

网页第二版中的 R、F、S、O 等协议组已经朝这个方向设计。建议要求每个科学判据同时给出**参照依据、允许误差、样本量、统计方法及失败判定方式**，而不仅是记录是否通过。

### **6.2 场数据必须拥有明确的空间语义**

在 `plugins/surrogate/models/pod.py` 中，模型要求场数据具有相同形状。这是必要的程序条件，但不是充分的物理条件。

两个数组即使形状一致，也未必代表相同位置、同一方向、同一种物理量。

对于不同骨模型、不同网格下的应力场或位移场，必须记录或建立：

- 共同参考坐标系及其变换。
- 网格、节点或采样位置的对应关系。
- 物理场单位、分量定义和张量坐标约定。
- 插值、配准或投影算子的身份及精度误差。

否则，代理模型可能学习到数值上结构整齐、物理上并不对应的场数据。

这是未来从单根骨优化走向跨骨泛化时，非常重要的前置条件。

### **6.3 数据冲突不能默认采用“第一份获胜”**

`plugins/surrogate/data.py:50–61` 在合并数据时，如果相同点哈希对应不同结果，会生成冲突说明，但保留第一次出现的数据。

这种策略作为临时去重方式可以理解，但不适合长期科学数据治理。

同一设计点可能因为网格、求解器、数值容差、执行环境或随机过程而出现不同结果。重复结果本身可能具有研究价值，不能在默认合并操作中被静默淘汰。

建议保留所有独立执行记录，并明确区分：

**真正重复且结果相同、不同执行产生的数值差异、输入指纹相同但执行身份不同、以及内容互相矛盾的数据。**

训练数据的选择策略可以由研究者指定，但应被登记为可复现的筛选规则，而不是依赖文件读取顺序。

## **七、建议的验收体系与实施顺序**

我建议不要立即全面扩展第二版科学验证代码。更合理的顺序是先让核心不变量真正成立，再建设独立科学验收，最后进行长期运行演练。

### **第一阶段：修复核心可信性问题**

目标：让系统能够可靠记账、识别计算、保护产物。

| 必须通过的验收场景           | 合格标准                   |
| ------------------- | ---------------------- |
| 任务成功后收到迟到的运行消息      | 成功状态不被覆盖               |
| 任务在运行中更换自由代码        | 拒绝不受控切换，或产生明确的任务级新执行身份 |
| 改变 `derive_def` 后重算 | 结果可区分，且能精确追溯推导量代码      |
| 发布操作的每个步骤发生崩溃       | 恢复后只有一份合法产物记录，哈希一致     |
| 子进程启动后核心立即崩溃        | 能认领、继续监控或安全清理原作业       |
| 备份文件发生等长度内容篡改       | 完整性核查失败                |
| 对多轮、大量任务追加记录        | 状态正确，性能满足预定义目标         |

这些测试应成为核心发布的强制门禁。

### **第二阶段：实现独立验证框架**

目标：证明验收运行本身可靠，不会错误复用数据、遗漏任务或误判成功。

优先实现 `campaign`、`preflight`、`runner` 和 `readback`，再接入完整科学分析模块。

其中，至少需要增加如下反例测试：

| 故意制造的问题                 | 验收程序必须表现               |
| ----------------------- | ---------------------- |
| 两次活动使用同一验证协议和行号         | 不能交叉读取实验               |
| 一个本应运行 100 点的实验只完成 97 点 | 明确不通过                  |
| 一个必需产物缺失                | 明确不通过                  |
| FEA 正常计算但很久没有新日志        | 不误判为卡死                 |
| 实际网格与请求网格不一致            | 不计入原指定网格等级的收敛分析        |
| 参数只通过 C 类探针验证           | 报告保留证据等级，不宣称实际运行值已独立验证 |
| 旧版本预测器与新版本实验混用          | 能定位执行来源，禁止错误归因         |

这里还要修正当前 `desk/core/check.py:45–50` 中一个验收语义问题：默认测试排除了 `cross`、`science`、`swap`。这本身可以作为快速检查的性能优化，但输出名称不应笼统称为“全部测试”。

建议明确区分 `quick`、`integration`、`recovery`、`cross-platform` 和 `scientific-validation` 等检查等级。不同等级分别报告结果，不能互相替代。

### **第三阶段：进行真实长期运行与恢复验收**

目标：证明平台能够跨版本、跨机器和跨故障长期保存科研证据。

| 长期运行场景               | 必须证明的性质                |
| -------------------- | ---------------------- |
| 运行中断、电源故障、核心重启       | 不丢失已确认结果，不错误重试成功任务     |
| Windows 与 Linux 协同运行 | 跨机器输入、产物和执行身份一致        |
| 代码、环境与求解器升级          | 历史结果仍能读取、解释，差异明确       |
| 备份后原机数据丢失            | 能在独立环境完成恢复和内容核验        |
| 数百到数千任务的实验记录         | 追加、检索、重放、追溯性能处于可接受范围   |
| 多版代理模型和 FEA 数据长期积累   | 无数据污染、无跨版本误用、训练集划分可复现  |
| 算法长期更新               | 旧实验仍可审计，不依赖当前插件代码来解释历史 |

我特别建议把**从备份恢复一个历史实验并完成追溯**列为强制验收，而不是可选的工程附加测试。长期科研平台的真正价值，最终要在这一场景中体现。

## **八、对于蓝图本身，我建议进行的有限修订**

我不建议重新设计整个 stem-lab 1.0。蓝图的简洁原则仍然成立，但应修订几项关键契约。

**修订一：身份从“输入身份”扩展到“执行身份”**

保留对象编号、点哈希和输入指纹；增加任务尝试、实际执行代码、环境和结果处理定义的不可变关联。

**修订二：任务状态转换成为契约中的一等公民**

明确任务转换表、终态约束、重试尝试及迟到消息处理规则，而不是仅校验结局名称是否合法。

**修订三：发布、恢复、备份具有统一的不变量**

每个阶段可以恢复，但不能绕过同一套内容校验；备份结果必须可独立核实。

**修订四：科学结果增加适用范围与验证证据**

尤其针对网格、物理场、材料参数、训练数据划分和预测器泛化，明确哪些是数学或科学前提，哪些只是软件格式条件。

**修订五：允许增加可重建的读模型**

原始账本仍是唯一权威，但允许带有日志头校验的缓存、索引和状态检查点，以满足多年运行后的规模需求。

此外，蓝图将契约与核心控制在约 3600 行作为设计目标，但网页实现中相应部分已明显超过这一规模，约为 5900 行 Python 代码。代码行数本身不是质量指标，不过这说明“固定的小”已经开始面临维护成本压力。

应优先检查能否进一步减少固定层的业务知识，而不是为了达到行数目标机械压缩代码。真正需要控制的是**冻结契约的复杂度、模块之间的耦合以及未来修改需要重新验证的影响范围**。

## **九、最终审查意见**

| 审查维度        | 结论               |
| ----------- | ---------------- |
| 总体架构方向      | 建议保留             |
| 科研数据身份与来路模型 | 方向正确，执行身份需扩展     |
| 实验与任务状态模型   | 需修复核心缺陷          |
| 故障恢复与产物发布   | 设计基础较好，尚需强化      |
| 跨机器与长期备份    | 未形成充分的恢复证明       |
| 现有自动化测试体系   | 覆盖方向较完整，缺少实际通过证据 |
| 第二版科学验证架构   | 值得继续实施，但需先修正骨架设计 |
| 长期计算科研适用性   | 有良好潜力，尚不具备正式验收条件 |

**我的核心建议是：保留 stem-lab 1.0 的整体结构，不进行大规模架构重写；优先修复任务状态不可逆性、任务级执行身份、产物恢复一致性和可验证备份，再实施第二版科学验收体系。**

这四项工作的价值高于继续增加插件功能，也高于立即引入新的技术栈。

对于一个计划使用数年的科研平台，最重要的设计指标不是现在可以跑多少计算，而是：**多年之后，面对某一项关键科研结论，系统能否毫不含糊地回答——它来自哪份物理模型、哪组输入、哪版实际执行代码、哪次求解、哪套数据处理过程，以及有哪些独立证据证明其可信。**

stem-lab 的蓝图已经围绕这个目标建立了正确的骨架。下一步的重点，是把这项原则从架构承诺落实为能够被故障注入、跨版本对比和科学基准实验反复证明的工程事实。
