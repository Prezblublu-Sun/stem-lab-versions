# **stem-lab 1.0 测试与长期验证体系建议**

结合图片中的 **Pre-production（上线前测试）→ Deploy（部署验证）→ Release（发布验证）→ Post-release（运行期验证）** 四个阶段，以及 stem-lab 当前的架构，我建议采用：

**契约驱动测试 + 性质测试 + 故障注入 + 科学基准验证 + 长期运行监测** 的组合。

不建议将图片中所有测试方法照搬。stem-lab 不是互联网在线服务，而是长期运行的计算科研平台，其核心目标是：

1. 科研结果真实、可追溯、可复现。
2. 计算任务在崩溃、重启、断网后能够正确恢复。
3. 实验数量和历史记录持续增加后，系统仍可使用。
4. 平台升级不能破坏旧数据和历史实验。
5. 验证程序能够主动发现错误，而不只是不断报告成功。

## **一、图片中的测试方法，哪些最适合 stem-lab？**

以下是针对当前平台的推荐优先级，而不是通用软件项目的优先级。

| 测试方法                          | 推荐程度     | 在 stem-lab 中的用途             |
| ----------------------------- | -------- | --------------------------- |
| Unit Tests 单元测试               | 必须       | 哈希、状态机、指纹、格式校验              |
| Property-based Tests 性质测试     | 必须       | 随机生成任务序列，验证不可变性和状态约束        |
| Contract Tests 契约测试           | 必须       | 保证插件、核心、历史格式兼容              |
| Mutation Tests 变异测试           | 必须（核心部分） | 证明验证器能发现被故意引入的错误            |
| Integration Tests 集成测试        | 必须       | 验证登记、运行、发布、追溯的完整流程          |
| Chaos Tests 故障注入              | 必须       | 崩溃、断网、进程残留、数据损坏             |
| Regression Tests 回归测试         | 必须       | 防止升级破坏旧科研结果                 |
| Benchmark / Load Tests 性能测试   | 必须       | 检查 JSONL 增长、检查点、并发任务        |
| Soak Tests 长稳测试               | 强烈推荐     | 连续运行数天，发现资源泄漏和状态异常          |
| Monitoring / Tracing 监测与追踪    | 必须       | 长期任务、存储、备份、资源、计算异常          |
| Scientific Acceptance 科学验收    | 必须       | FEA 数值正确性、代理精度、优化结果有效性      |
| Static Analysis 静态检查          | 强烈推荐     | 固定核心的类型、依赖、潜在错误             |
| Fuzz Tests 模糊测试               | 推荐       | JSONL、manifest、损坏文件及异常输入    |
| Canary / Shadow Tests 灰度与影子测试 | 推荐       | 新版插件或策略与旧版比较，不影响正式结果        |
| Formal Verification 形式化验证     | 选择性      | 任务状态转换、锁序、不可变性等关键规则         |
| A/B Tests、流量实验                | 暂不优先     | 面向用户流量的传统形式不适用，可转化为科研算法对照实验 |
| Penetration / UI Tests        | 按需       | 多用户或网络开放后提高优先级              |

这里最重要的是：**科研科学验证与软件工程测试不能互相替代。** 通过 500 个单元测试，也不能证明 FEA 应力结果在物理上可信。

## **二、建议采用的四阶段验证体系**

01

开发检查

每次提交

单元 / 契约 / 性质

02

集成验收

每次合并

端到端 / 崩溃 / 跨平台

03

发布验证

版本发布

真实小任务 / 新旧对照

04

长期监测

持续运行

监测 / 长稳 / 恢复演练

四阶段形成一个循环：运行期发现的真实故障，应转化为自动化回归测试，再进入下一次开发与发布检查。

### **阶段一：Pre-production —— 开发阶段验证**

这一阶段应该重点围绕 `stemlab/contract/` 和固定核心进行。

#### **A. 单元测试 + 性质测试：验证核心不变量**

我最推荐将现有 `pytest` 和 [Hypothesis Stateful Testing](https://hypothesis.readthedocs.io/en/latest/stateful.html?utm_source=chatgpt.com) 结合使用。

普通单元测试检查人为编写的案例；Hypothesis 可以生成大量输入和操作序列，尤其适合有状态的 API。

[image](https://www.google.com/s2/favicons?domain=https://www.pytest.org\&sz=32)

pytest documentation+1



重点测试：

| 核心模块                  | 应当始终成立的性质               |
| --------------------- | ----------------------- |
| `contract/states.py`  | 合法状态转换确定；终态不得非法回退       |
| `contract/chain.py`   | 任意合法链都能验证；修改历史字节必被检测    |
| `contract/hashing.py` | 同内容跨 Windows/Linux 哈希一致 |
| `experiments/log.py`  | 并发合法追加不丢记录、不重复编号        |
| `hooks/publish.py`    | 发布和恢复重复执行，最终状态一致        |
| `plugins/fea/run.py`  | 同一物理槽不会被两个有效租约同时持有      |
| 新增检查点                 | 从检查点恢复的状态等于完整日志折叠的状态    |

特别推荐使用 Hypothesis 的状态机测试，随机产生这样的序列：

`创建 → 填输入 → 启动 → 报任务 → 失败 → 重试 → 停止 → 重启 → 发布`

每一步检查契约不变量，而不是只检查最后的成功结果。

这一方法能够发现人工编写的测试中容易遗漏的非法操作顺序。

#### **B. Mutation Tests：验证测试本身的有效性**

这是我认为最值得引入的新方法之一。

例如，假设 `_task_ok()` 中存在：

```
if task_is_terminal:    return False
```

变异测试工具可以故意修改条件或返回值，观察现有测试是否失败。

如果修改后测试依然全部通过，意味着你的测试可能没有真正保护这项规则。

推荐使用 [mutmut](https://mutmut.readthedocs.io/en/latest/?utm_source=chatgpt.com)，但优先在 Linux 环境运行。其当前文档所述的主要进程隔离机制依赖 POSIX `fork`，因此不建议将 Windows 作为唯一的变异测试执行环境。

[image](https://www.google.com/s2/favicons?domain=https://mutmut.readthedocs.io\&sz=32)

python mutation tester — mutmut documentation



不必对整个项目执行昂贵的变异测试。优先覆盖五个位置：

1. 状态转移规则。
2. 哈希链验证。
3. 任务执行身份。
4. 产物发布与恢复。
5. 求解槽租约与释放条件。

**建议的验收规则：** 对每条关键不变量，至少准备一个故意违反它的反例，确保测试确实能够检测到该问题。

不要把全项目变异分数当作唯一指标。科研平台最重要的是关键错误能否被识别，而不是得到一个漂亮的百分比。

#### **C. 静态分析与依赖约束**

建议采用一个较小的工具集合：

| 工具                                                                 | 用途               |
| ------------------------------------------------------------------ | ---------------- |
| [Ruff](https://docs.astral.sh/ruff/linter/?utm_source=chatgpt.com) | Python 静态检查和代码规范 |
| Mypy 或 Pyright                                                     | 类型检查，优先应用于固定核心   |
| import-linter                                                      | 检查四层架构的依赖方向      |
| `pytest-cov`                                                       | 查看关键分支是否真正执行     |
| `mutmut`                                                           | 检查测试是否能够识别错误实现   |

Ruff 适合频繁运行，不需要将所有检查都改造成复杂流程。

[image](https://www.google.com/s2/favicons?domain=https://docs.astral.sh\&sz=32)

Ruff



我建议契约和核心采用严格检查，算法插件使用相对宽松的规则。这样符合蓝图“固定的小、自由的大”的原则。

### **阶段二：Deploy —— 集成、故障、性能和跨机器测试**

这是 stem-lab 最容易发现严重工程问题的阶段。

#### **A. 端到端集成测试**

应该建立一套独立于生产数据的最小科研流程：

登记骨模型、内核、设定与输入点

创建并启动 FEA 实验

执行小规模求解、发布数据与归档

读取产物并核对任务执行身份

恢复历史实验并验证完整追溯链

这里要有两个版本：

**模拟求解版本：** 使用非常快的假求解器，适合每次合并时运行，重点验证执行编排和记录正确性。

**真实求解版本：** 使用经过严格定义的小型 FEA 算例，验证实际求解器接入、参数回读和产物处理。可以在发布前运行，不必每次改代码都运行。

#### **B. Chaos Testing：故障注入**

对 stem-lab，故障注入比传统网站的流量压测更重要。

| 注入故障                  | 必须满足的结果          |
| --------------------- | ---------------- |
| 写 JSONL 时强制结束进程       | 半行恢复后，完整历史不被损坏   |
| 发布产物到第 3、4、5 步时崩溃     | 重启后唯一登记且内容哈希正确   |
| 子进程创建后立即杀死核心          | 不能同时出现两个有效求解槽拥有者 |
| Linux GPU 作业运行时断开 SSH | 不把网络故障误判为科学失败    |
| 任务完成后重复发送成功消息         | 不改变任务身份或结果       |
| 备份途中断开网络              | 能识别不完整备份并重试      |
| 人为损坏一个历史产物            | 核验失败，不能被检查点或缓存掩盖 |
| 删除、损坏状态检查点            | 从原始日志重新构建正确状态    |

这类测试应通过自建故障注入点，在测试环境中精确触发，而不是随机杀死所有进程。

对于每个具有多步持久化操作的模块，应当能够指定“在第几步之后中断”，并在恢复后检查完整性。

#### **C. Benchmark + Load：验证 JSONL 与检查点扩展能力**

推荐 `pytest-benchmark`，它支持基准测试、统计结果、历史对比和 JSON 导出。

[image](https://www.google.com/s2/favicons?domain=https://pytest-benchmark.readthedocs.io\&sz=32)

pytest-benchmark.readthedocs.io



建议采用以下工作负载：

| 单实验记录数    | 测试目的       |
| --------- | ---------- |
| 1,000     | 基本功能       |
| 10,000    | 常规科研实验     |
| 100,000   | 长时间任务与频繁事件 |
| 1,000,000 | 容量边界评估     |

每种规模测量：

- 单次 `append()` 延迟及其 P95/P99。
- `fold()` 完整重放耗时。
- 检查点恢复耗时。
- `board` 读取当前状态的耗时。
- `check_chain()` 全量核验耗时。
- 进程内存峰值和磁盘读写量。

不要只测每秒能写多少记录。最有价值的是观察性能增长曲线：引入检查点后，日常追加和状态读取是否摆脱了对全量历史长度的依赖。

同时比较 Windows 和 Linux 的行为，但平台真实单写入节点仍是 Windows。

#### **D. Soak Testing：长时间稳定性测试**

建议用模拟任务连续运行 24—72 小时，观察：

- 是否发生内存持续增长。
- 是否有进程或文件句柄泄漏。
- 求解槽是否能够完全释放。
- 日志是否持续合法。
- 检查点是否始终可以重建。
- 轮询器和备份是否影响任务执行。

不需要让昂贵的真实 FEA 求解器连续运行三天来验证事件日志和调度器。模拟工作负载通常更适合暴露此类工程问题。

### **阶段三：Release —— 科研系统中的灰度与影子验证**

图片中的 Canary、Shadowing、Traffic Shaping 和 Feature Flagging，主要用于线上服务部署。

对 stem-lab，可以把它们改造成**科研代码版本比较与受控升级机制**。

| 原方法                 | 在 stem-lab 中的改造             |
| ------------------- | --------------------------- |
| Canary（金丝雀测试）       | 新版核心或插件先运行少量标准科研算例          |
| Shadowing（影子运行）     | 新旧插件对同一份输入分别计算，比较结果，不覆盖正式数据 |
| Tap Compare（流量分流对比） | 复制相同科研任务给新旧执行实现，按任务身份对齐结果   |
| Feature Flags（功能开关） | 新的检查点、数据处理或插件接口通过明确配置启用     |
| Monitoring（监测）      | 观察新版的任务错误率、资源使用、产物完整性和执行时间  |

例如，准备一组固定的 FEA 基准算例，在更新插件之前和之后分别运行。

然后比较：

- 输入与执行身份是否正确。
- 模型是否使用相同几何、材料和边界条件。
- 网格数量、求解收敛行为是否符合预期。
- 位移、应力和推导量变化是否在允许范围内。
- 计算时间、内存及产物规模是否出现异常增长。

对于代理模型，还应比较预测误差分布、不确定度校准和不同骨模型上的泛化表现。

有一点非常重要：

**新版和旧版的结果不必数值完全相等，但差异必须得到解释。**

例如升级求解器后得到略有差异的应力结果，可能是合理的数值变化；验收程序不应只因为哈希不同就判失败。

对于执行框架自身，任务身份、哈希链、输入指纹等仍应严格一致。

正式发布阶段需要采取“失败即拒绝升级”的策略，而不是让新版自动替换已经运行的历史实验。

### **阶段四：Post-release —— 长期运行验证**

图片右侧的 Monitoring、Profiling、Logs/Events、Chaos Testing、Tracing 和 Auditing，对 stem-lab 都有意义。

但这里最重要的变化是：**测试不再只是开发者主动执行，而要成为平台的日常运行行为。**

#### **A. 建议持续监测的关键指标**

| 类别    | 指标                      | 异常动作       |
| ----- | ----------------------- | ---------- |
| 实验运行  | 值守心跳、启动时长、任务进展          | 告警、人工核查    |
| 计算资源  | 求解槽持有者、租约时长、孤儿进程        | 告警、受控回收    |
| 数据完整性 | 日志链头、未核验产物、检查点一致性       | 停止不安全发布    |
| 备份    | 最近成功时间、校验结果、恢复演练状态      | 重试并主动送达    |
| 系统性能  | append P95、fold 耗时、内存占用 | 标记性能退化     |
| 科研任务  | FEA 失败原因、求解残差、异常结果比例    | 按科学判据进一步检查 |
| 模型质量  | 预测误差、训练数据变化、泛化性能        | 重新科学验收     |

#### **B. 监控工具的选择**

对于目前的两台机器，我建议**先使用现有&#x20;**`board/alerts.py`**&#x20;加轻量送达机制**，不急于建设完整监控平台。

可以直接使用：

- Windows Task Scheduler：定期备份和健康检查。
- Linux `systemd timer`：定期执行远端检查。
- Python `logging` + JSON 日志：记录执行尝试、错误、耗时。
- 邮件或 Webhook：关键告警的主动送达。

当指标数量、历史趋势和告警路由需要增长时，再考虑以下组合：

**Prometheus + Alertmanager**：负责指标监测、告警分组、路由和通知。

[image](https://www.google.com/s2/favicons?domain=https://prometheus.io\&sz=32)

Prometheus



**OpenTelemetry**：用于跨 Windows 核心、远端 Linux worker 和任务进程的关联追踪。可以用相同的 `experiment_id`、`round_id`、`task_id`、`attempt_id` 关联执行事件。

[image](https://www.google.com/s2/favicons?domain=https://opentelemetry.io\&sz=32)

OpenTelemetry



注意，监测系统不应成为新的权威科研账本。它用于诊断运行状态，科研身份和结果仍由 stem-lab 的原始记录保存。

#### **C. 运行期的合成测试**

除了被动监控，建议定期启动一项极小规模的健康实验：

`创建实验 → 启动模拟任务 → 发布产物 → 回读 → 核验哈希 → 结束`

这相当于图片中的 Canarying 和 Dynamic Exploration。

合成实验必须使用独立的测试账本或明确的隔离命名空间，不能污染正式科研数据。它可以验证的不仅是进程仍然存在，还包括整条科研执行路径是否实际可用。

## **三、针对科研正确性，增加一条独立验证主线**

图片主要描述软件系统的质量保障，但 stem-lab 还需要科学计算领域特有的 Verification & Validation（V&V）。

这是不能省略的一部分。

| 科研模块           | 推荐验证方法               | 核心指标              |
| -------------- | -------------------- | ----------------- |
| `recon` 骨重建    | 几何基准测试、人工复核、敏感性分析    | 几何误差、坐标一致性、单位正确性  |
| `fea` 有限元      | 解析解对照、网格收敛、平衡检查、独立基准 | 位移/应力误差、残差、网格收敛   |
| `surrogate` 代理 | 独立测试集、分组交叉验证、重复训练    | RMSE、MAE、误差分布、泛化性 |
| `opt` 优化       | 已知最优解、小型穷举基准、多随机种子比较 | 可行性、最优性差距、计算预算    |
| 科研闭环           | 预测—真实 FEA 对照         | 推荐方案的真实表现及预测误差    |

特别建议在代理训练中根据骨标识进行分组划分，防止同一根骨的高度相关样本同时进入训练和测试集，造成泛化性能高估。

对于 FEA，不应仅用“求解器成功返回”作为科学通过条件。还需要独立检查模型质量、守恒关系、网格敏感性和必要的实验依据。

科学验收应允许三种结论：`PASS`、`FAIL`、`INDETERMINATE`。缺少参考数据或样本量不足时，不能自动判断通过。

## **四、推荐采用的最小工具栈**

不建议一次安装大量测试工具。我推荐从以下组合开始：

| 工具                 | 主要职责          | 执行位置            |
| ------------------ | ------------- | --------------- |
| `pytest`           | 单元、契约、集成、回归测试 | Windows + Linux |
| `Hypothesis`       | 性质测试、随机状态序列   | Windows + Linux |
| `Ruff`             | 快速静态检查        | CI              |
| `Mypy` / `Pyright` | 固定核心的类型检查     | CI              |
| `import-linter`    | 分层依赖约束        | CI              |
| `pytest-cov`       | 分支覆盖率         | CI              |
| `mutmut`           | 核心保护逻辑的变异测试   | Linux           |
| `pytest-benchmark` | 日志、检查点、查询基准   | 固定性能测试环境        |
| `pytest-xdist`     | 加速独立测试执行      | CI，按需使用         |
| 自建 fault injector  | 进程崩溃、断网、发布中断  | 隔离测试环境          |
| OS 定时调度 + 告警       | 备份和持续健康检查     | 实际运行机器          |

`pytest-xdist` 适合并行运行彼此独立的测试，但涉及全局求解槽、单写入者和共享文件锁的并发测试，应使用明确的并发场景，而不能随意交给测试框架随机并行。

### **建议的执行频率**

| 时间     | 执行内容                                 |
| ------ | ------------------------------------ |
| 每次提交   | Ruff、类型检查、架构约束、快速单元与契约测试             |
| 每次合并   | 完整核心测试、性质测试、模拟端到端测试、Windows/Linux 检查 |
| 每晚     | 故障注入、变异测试、性能回归                       |
| 每周     | 长稳测试、备份完整性检查、必要的真实计算烟雾测试             |
| 每次正式发布 | 真实科研基准、旧版对照、格式迁移、恢复测试                |
| 持续运行   | 心跳、资源租约、任务状态、磁盘、备份、告警送达              |
| 定期演练   | 独立恢复历史数据及科研证据链                       |

这是推荐的目标节奏，可以按当前机器算力和测试成本调整。

## **五、如何判断整套验证体系是否真正有效？**

我建议不要以“通过多少个测试函数”为核心指标，而是建立以下五个验收条件。

1

**核心不变量通过**

状态、身份、哈希、资源租约和发布规则均有正向测试与反向测试

2

**错误能够被检测**

对关键逻辑故意注入错误，验证器能够可靠判失败

3

**故障能够恢复**

每个关键崩溃边界都有确定的恢复结果，且无数据错误归属

4

**性能增长可预测**

日志和数据规模增长时有基准曲线、容量预算与明确阈值

5

**历史科研结果可独立验证**

旧代码、旧格式、备份恢复后的结果仍能被解释和核对

**我的最终建议是采用“少量高价值工具 + 四阶段验证 + 独立科学 V&V”的体系。**

现在最值得投入的是 `pytest + Hypothesis + mutmut + 故障注入框架`，优先验证执行身份、状态机、槽租约、产物恢复；然后使用 `pytest-benchmark` 建立检查点的性能证据，并完善备份与主动告警。

不必把互联网服务中所有灰度、流量控制、A/B 测试机制都移植过来。对 stem-lab 更有价值的是**固定科研输入的新旧版本对照、真实求解验证，以及长期故障恢复演练**。

最终要达到的状态是：**开发阶段能发现错误，集成阶段能证明恢复，发布阶段能识别科学差异，运行阶段能主动发现并处理故障。** 这才是适合长期计算科研平台的完整验证体系。
