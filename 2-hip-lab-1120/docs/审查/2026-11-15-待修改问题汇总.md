# **stem-lab 1.0 待修改问题汇总**

基于《stem-lab 1.0 蓝图》、最新版《stem-lab 架构与验证代码 (2).html》以及前几轮审查结论，整理如下。

**总体建议：保留当前四层架构、八种实验类型和 JSONL 权威账本，不进行整体重构。重点补齐执行身份、故障恢复、增量状态和科学验证四项能力。**

## **一、待修改问题清单**

P0 · 立即修改

影响科研可信性或核心运行正确性

| 编号 | 问题             | 需要修改的内容                                                          |
| -- | -------------- | ---------------------------------------------------------------- |
| 01 | **任务级执行身份缺失**  | 增加 attempt_id 和不可变 execution_manifest，绑定实际代码、求解器、环境和结果行；保留现有输入指纹 |
| 02 | **求解槽所有权不完整**  | 引入 lease_id；修复进程启动与槽交接的崩溃窗口；防止旧执行释放新槽；确认孤儿进程真正退出                 |
| 03 | **任务终态身份可被覆盖** | 终态重复消息不得改变 fingerprint、执行身份等关键字段；明确幂等更新规则                        |
| 04 | **产物恢复最终核验不足** | 已登记但未记 output 的产物，补写记录前必须重新核对内容哈希；保证发布恢复幂等                       |

P1 · 核心完善阶段

长期无人值守和正式科学验收前完成

| 编号 | 问题              | 需要修改的内容                                                                   |
| -- | --------------- | ------------------------------------------------------------------------- |
| 05 | **无人值守运维闭环不足**  | 建立周期备份、失败重试、主动告警送达、告警升级、状态确认和定期恢复演练；可使用操作系统调度器                            |
| 06 | **全量重放造成性能增长**  | 为实验记录和登记链设计增量索引、状态检查点、失效检测和可重建机制；周期性完整核验仍保留                               |
| 07 | **独立科学验证框架未实现** | 实现 validation/ 最小闭环：preflight、runner、readback、分析报告、验证活动唯一身份及测试隔离          |
| 08 | **验证器自身缺反向测试**  | 建立故意错误输入、错误指纹、缺失任务、错误产物和崩溃注入；建立契约规则到测试的覆盖映射                               |
| 09 | **科学判据存在边界错误**  | 修复 surrogate.report 的 n=0 仍可能通过；明确 PASS/FAIL/INDETERMINATE；不同物理量使用各自的数值容差 |
| 10 | **格式与插件兼容政策不足** | 保存各格式版本 golden 样本；加入逐版本迁移和端到端读取测试；明确插件 API 版本兼容规则                         |
| 11 | **备份历史完整性不足**   | 建立增量内容校验、周期性全量校验、独立恢复验证；检查备份链头与实际产物的一致性                                   |

P2 · 长期演进

现在确定原则，按研究规模逐步实现

| 编号 | 问题                | 需要修改的内容                                                   |
| -- | ----------------- | --------------------------------------------------------- |
| 12 | **数据生命周期没有完整策略**  | 区分临时文件、正式产物、可归档大文件；规定保留、清理、迁移和恢复策略，不采用简单的引用计数自动删除         |
| 13 | **操作者身份记录不统一**    | 定义 actor/operator 及系统服务身份；历史记录缺失身份时解释为 unknown，暂不建设完整 ACL |
| 14 | **插件缺少执行权限隔离**    | 保留 Handle 接口；未来允许不可信插件时，增加独立进程、文件权限及资源隔离                  |
| 15 | **科学数据冲突处理较简单**   | 代理训练不能仅依赖 first 规则选择冲突结果；保留来源及冲突证据，登记明确的数据筛选策略            |
| 16 | **跨骨模型场数据语义约束不足** | 明确坐标系、单位、网格对应、插值算子和误差；避免代理模型学习物理位置不一致的场数据                 |

## **二、最优先修改的代码位置**

| 修改目标       | 主要涉及模块                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------- |
| 执行身份和数据溯源  | `contract/entries.py`、`contract/states.py`、`contract/plugin_api.py`、`plugins/fea/jobs.py` |
| 求解槽租约及崩溃恢复 | `plugins/fea/run.py`、`hooks/remote.py`                                                    |
| 任务终态保护     | `contract/states.py`、`tests/contract/test_states.py`                                      |
| 产物发布一致性    | `hooks/publish.py`、`registry/verify.py`                                                   |
| 增量状态和检查点   | `experiments/log.py`、`experiments/view.py`、`registry/register.py`、`contract/chain.py`     |
| 自动备份与运维告警  | `desk/core/backup.py`、`desk/core/check.py`、`board/alerts.py`                              |

这些是主要涉及位置，不代表所有文件都必须修改。特别是契约层，应先确定新增字段的语义及格式版本，再决定如何实现。

## **三、建议的实施顺序**

1. **阶段一：核心可信性收口**

   完成 01—04。重点保证每项科研结果具有精确执行身份，任务不可被错误改写，崩溃恢复不会造成重复执行或错误发布。

   正式科研运行的核心前提
2. **阶段二：长期运行能力**

   完成 05、06、11。建设自动备份、告警、恢复演练与增量状态机制，并用压力测试确定性能验收标准。
3. **阶段三：独立科学验收**

   完成 07—10。实现真正能够运行的验证框架、反向测试、覆盖矩阵及格式兼容测试。

   注意：前两个阶段各项修改的反向测试应同步编写，不应等到第三阶段才开始。
4. **阶段四：长期数据治理**

   处理 12—16。首先确定身份、数据保留、冲突处理和物理语义规则；多用户权限、冷存储与插件沙箱可按实际需求实施。

## **四、明确不建议修改的部分**

目前没有充分理由改变这些已有设计：

- 四层架构以及核心与插件的依赖方向。
- Windows 单写入者原则。
- JSONL 追加日志及哈希链作为权威记录。
- 实验、轮次、任务的基本层次关系。
- 八种实验类型及十六种登记对象。
- 冻结核心、自由算法插件的开发模式。
- FROZEN 目录及内容哈希校验机制。
- 验证账本隔离、真实硬件资源预算统一的原则。

这些属于应该继续保留的架构基础，后续修改以增强其不变量为主。

## **五、最终归纳**

## **16 项待处理问题，归结为 4 个核心建设方向**

# **01**

**可信执行**

执行身份、任务状态、资源租约、产物一致性

# **02**

**可恢复运行**

备份、告警、故障恢复、增量检查点

# **03**

**独立科学验证**

验证框架、反向测试、科学判据、兼容性

# **04**

**长期数据治理**

归档、操作身份、插件隔离、数据物理语义

**最重要的建议：优先完成前四项 P0 修改，然后以现有架构进行一次完整的故障注入、恢复和追溯验收。**

只有在能证明“计算结果不会错认身份、任务不会被错误重排、资源不会错误释放、产物不会错误登记”之后，才有必要投入更多精力建设长期运维和大规模科学验证。

这样可以用最少的架构改动，最大程度提高 stem-lab 作为长期计算科研平台的可信性和可维护性。
