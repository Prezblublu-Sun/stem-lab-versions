# 测试建议的评估（2026-11-15）

评估的对象是 [2026-11-15-测试与长期验证体系建议.md](2026-11-15-测试与长期验证体系建议.md)。每条都对着现在的代码、测试和
[2026-11-15-修改目标.md](2026-11-15-修改目标.md) 核过。标记的意思：

- 【已有】已经在做，或已有测试守着；
- 【在做】另一个会话正在写（补 02、04 的测试：求解槽、发布）；
- 【采纳】值得做，还没做；
- 【改】方向对，要按这里的情况改了再做；
- 【不做】这里用不上；
- 【等你定】要先等《修改目标》里你定的那几条。

对话里先给过一版评估。存的时候对着原文又核了一遍，有四处当时说得不准，这里已改正：

- 监控：它本来就主张先用 `board/alerts.py` 加轻量送达，Prometheus 那些是“以后再考虑”；
- 并行跑测试：它自己也说碰求解槽、单写入者和文件锁的测试不能随意并行；
- 功能开关：它说的是“通过明确配置启用”，和这里的要求不冲突，只差一条：要记进来历；
- “失败即拒绝升级”：它已经把执行框架的严格一致和科学结果的“差异要解释”分开了。

## 一、总的看法

方向对，和现在的做法大体一致。它也不主张照搬，多处写了“先用轻量的”。最有用的几样已经在用：
属性测试和随机操作序列（Hypothesis）、故意制造故障、变异测试、每条目标配一种测试来证明。
今天的属性测试查出四处，都已修好（见《修改目标》“已经做了的”）。

和这里对不上的主要有三处：

1. 它假设有 CI 服务器和合并流程。这里是一个人、两台机器，提交前钩子跑一遍完整检查（约 8 分钟）。
2. 它让测试在 Windows 和 Linux 两边都跑，变异测试放在 Linux 上。这里账本只在 Windows 这台写；worker 只装运行要用的几组
   （不装开发依赖，也不装 CT 那组），只做训练。
3. 它没算加测试的代价。它建议的新测试多数要放进 `tests/`（固定部分），每加一批都要你认，再由你重新生成 FROZEN；
   固定部分能有多少行也还等你定。所以测试要挑着加，不是越多越好。

#### 阶段一 B：变异测试

- 工具：【改】用 pytest-gremlins，不用 mutmut。gremlins 在这台 Windows 上直接跑，不改盘上的文件。mutmut 要 Linux 或 WSL，
  用它就得在 worker 上另装一套开发环境、另放一份仓库，而 worker 只该放训练要的东西。gremlins 还新，出怪事再换。
- 试过 `chain.py`：改坏 44 处，原来的测试发现 38 处，补测试后 40 处，剩 4 处改了也不改变行为。
- 它列的五处（状态转移、哈希链、任务身份、发布和恢复、求解槽）：【采纳】哈希链做过了，其余四处照同样的做法跑一遍，补上漏掉的测试。
- “每条关键规则至少有一个故意违反它的反例”“不拿变异分数当唯一指标”：同意。现在的做法是：还没做到的目标写成
  `xfail(strict=True)`，找到的反例写成 `@example`。

#### 阶段一 C：静态检查

- ruff、import-linter：【已有】。
- 类型检查（mypy / pyright）：【采纳】以后先对契约和挂点开。现在开多半先冒出一大批要改的地方，排在框架搭完之后。
- 覆盖率（pytest-cov）：偶尔跑一次找没测到的分支，不设门槛：跑到了不等于验对了。
- “契约和核心严格、插件宽松”：同意。现在 ruff 全仓库同一套基本规则，以后给契约和核心多开几类。

- 真实求解的一套：【已有】科学验收里的小算例（要 Abaqus），平时不跑，要用时单独跑。

#### 阶段二 C：性能

【改】【等你定】一千、一万、十万、一百万条四档（最后一档它标的是“容量边界评估”）不是从这里的实际出发的。
档位应从实际规模推：一个实验多少点、多少轮、账本存几年（《修改目标》里等你定的“规模的数”），在那之上留十倍余量。
现在已经看得见的慢处是 `query._used` 每次都扫一遍全部实验，先测它比造一百万条记录有用。台式机上波动大，基准只看走势、不设线。

“Windows 和 Linux 都比”：【不做】账本只在 Windows 这台写（它自己也说单写入的是 Windows）。

#### 阶段二 D：长稳

【采纳】等验证代码搭起来再做：用验证自己的账（`H:\stemlab-validation\`），测试插件代替求解，先跑几个小时，再到一两天。
看它列的那几样：内存、进程和文件句柄、求解槽放没放、账本合不合法。这台是你平时用的台式机，挑不用的时候跑。

#### 阶段三：新旧对照

- 灰度、影子、分流对比：【采纳】就是《验证实验》里新旧对照的做法（设计已有，代码没写）。用克隆的实验跑，不碰正式数据。
- 功能开关：同意“明确配置启用”，再加一条：开关要是登记过的设置，记进那一轮的来历；不能用环境变量临时开，否则一条记录说不清
  当时开没开，结果复现不了。另有一件该先改的：现在多数设置读不到就用默认值，写了不认识的项会被悄悄忽略（CT 那几项例外），
  应改成拒收（《验证代码》第四节）。
- “差异必须得到解释”“执行框架的身份、哈希链、指纹严格一致”：同意。
- “失败即拒绝升级”：框架的规矩（身份、哈希链、断了能恢复、发布不重复）不过就不升级，同意。科学上的对照差异：解释、记下，
  不自动挡升级。你已经定了，科学验收只评估、不挡发布。
- 代理模型“在不同骨模型上的泛化”：现在测不了，见第三部分第 3 条。

#### 阶段四：运行期

- 指标表：同意大方向。对着仪表盘现有的逐项补，先补数据完整性和求解槽两类（出事的代价最大）。
- 监控工具：同意它的意见，先用 `board/alerts.py` 加轻量送达，加系统自带的定时任务（Windows 的任务计划程序、Linux 的定时任务）。
  送到哪、多久一次【等你定】。Prometheus、Alertmanager、OpenTelemetry：一个人两台机器，多半一直用不上。
  它提的每次尝试一个编号（attempt_id），要等 01（一轮中途改了代码怎么算）定了再说。
- “监测不能成为新的科研账本”：同意，和蓝图一致。
- 合成的健康实验：【采纳】值得做，它其实是《验证代码》要搭的一部分。两个条件：记在验证自己的账上，不进 `data\`；
  它也占求解槽，要排在不和真实验抢槽的时候。

### 第三节　科学上的验证（V&V）

### 第五节　五条验收

1. 核心规则有正反两面的测试：同意。状态、身份、哈希已有；求解槽和发布在做。
2. 错误能被查出来：同意，靠变异测试和 `xfail` / `@example`。
3. 故障能恢复：同意。半行、发布已有；求解槽的交接在做。
4. 性能增长可预测：要等规模的数。
5. 历史结果能独立核对：同意，要补一条具体的测试【采纳】：规则收紧以后，用新代码核旧账本。账本核对时会用现在的规则重查每条
   旧记录，规则一收紧，旧记录就可能被判不合法。今天状态表收紧了两处，真账本里没有受影响的记录（只有一个没启动的实验），
   以后再收紧要有测试守着。

## 三、它没提到的三样

1. **环境会悄悄变。**这里真出过的事多是这一类：360 把刚装的库占住（11-14、11-15 各一次）；改了锁之后 worker 要跟着重装；
   Abaqus 的许可也可能哪天连不上。【采纳】加一条“开工前体检”，几秒钟查完这几样，出了问题说清是哪一样、该谁处理。
   worker 那一半，`python worker_env/sync.py --check` 已经能查。
2. **你自己能不能用操作台。**它把界面测试放在“按需”。现在的问题不是页面会不会坏，而是你没法按你懂的方式调设置。页面怎么接，
   你说了自己来理，所以界面的自动测试等页面定下来再加；在那之前该验的是“你能不能只靠页面跑完一个实验”。
3. **数据只有一根骨头。**它建议代理按骨头分组划分训练集和检验集，代码已经支持；但现在只有一根骨头的数据，
   “能不能推广到别的骨头”测不了。有第二根之前，报告里不该出现这样的结论。

## 四、值得采纳、还没做的

按值不值排：

1. 合成的健康实验（并进《验证代码》）。
2. 开工前体检。
3. 性能档位从实际规模推，先测 `query._used`（要先定规模的数）。
4. 规则收紧后用新代码核旧账本的测试。
5. 变异测试扩到状态转移、任务身份、发布、求解槽。
6. 操作台核心那一层的随机操作序列。
7. 登记清单和各格式核对的随机输入测试。
8. 长稳测试（等验证代码）。
9. 类型检查（框架搭完之后）。

动手和《修改目标》里其他等你定的一起，由你定。这份评估没有改《修改目标》：另一个会话正在改它（补 02、04 的测试），
免得两边同时改一份文件。
