# 验证代码怎么搭（第二版）

验证代码只做一件事：在系统的某一个提交上，照预登记的试验说明把验证试验跑一遍，逐行核对真的是照说明跑的，
再照事先定好的分析出报告。试验本身怎么设计，见 [验证实验.md](验证实验.md)；这份只讲代码。代码还没写。

第一版的骨架不变：试验说明 → 设计表 → 隔开的仓库和账 → 逐行跑 → 结果 → 分析 → 报告。
第二版根据下面三条认识改了六处，见第二节。

## 一、三条认识

### 1. 因素写在三种地方，可靠程度差得很远

| | 点里 | 包 | 设定里 |
| --- | --- | --- | --- |
| 是什么 | 每个点的设计和条件：柄的几何、过盈、摩擦、松质模量、载荷、界面网格尺寸 | 用哪个内核、哪个策略、哪个预测器、哪份推导量定义 | 重建的阈值和平滑、代理的模型选项、候选池的取法 |
| 由谁规定 | 内核包的清单：每一项的名字、单位、含义 | 包的哈希 | 各个插件自己定，没有一处写全 |
| 写错或改名 | 启动时逐项核：点带的项和内核要的差一项，就启动不了 | 哈希对不上就不跑 | 多数是“读不到就用默认值”，悄悄忽略（重建设定里 CT 那几项例外：不认识的名字会被拒） |
| 默认值 | 没有：契约要求每个点的条件写全 | 没有 | 有，藏在插件的代码里 |
| 跑完能不能核 | 能：数据的每一行原样带回设计和条件；有几项另外回写实际用的值（界面网格实际划成的尺寸 `h_mesh_mm`，实际加的载荷 `load_x_N`、`load_y_N`、`load_z_N`） | 能：用了哪个包由核心记进这一轮的来历，不靠插件自己报 | 要看插件：代理把实际用的模型选项写进了误差报告和预测器；重建 CT 那几项只写在 history 的文字里；三角网边长、候选池的取法哪里都没有回写 |

FEA 的因素全在点里和包里，系统已经替我们把保险做了大半。需要验证代码自己补的，是重建、代理、优化写在设定里的那些项。

### 2. 验证代码自己也不能“读不到就用默认值”

读试验说明、读产物、读回写，只要读不到就停下，并说出缺的是什么。系统的那个毛病，验证代码自己也可能犯；
它要是也犯，三道保险就形同虚设。

### 3. 有三处会和你真实的账碰上

- **远端的作业文件夹按实验编号起名**（`作业根目录/E0012/r1`）。验证另起一本账，编号也从 E0001 开始，
  和你用同一个作业根目录，就会和你的实验撞在一起。所以验证要用自己的作业根目录。
- **FEA 的归档位置写在导出设定里**（`archive_root`）。照抄你平时的导出设定，验证的归档就会落进你的归档。
  所以验证要用一份自己的导出设定。
- **求解槽是整台机器共用的**（默认在 `%LOCALAPPDATA%\stemlab\slots`；2026-11-15 之前在用户临时目录下的 `stemlab-slots`）。
  这一处不隔开才是对的：验证和你自己的实验共用同一组槽，
  加起来不会超过上限。所以验证要明写用这一组，不另开一组，也不依赖进程是谁起的。

## 二、第二版改了什么

1. **因素分三级核**（第四节）。每个因素在适配表里写明属于哪一级、用什么办法核。
2. **三道保险成了流水线里固定的三步**（第五节），不再是附加的检查。
3. **只经一个文件和系统打交道**（接口层 `port.py`），而且只碰固定的部分：实验类型的三张表、核心的动作、
   登记的东西的格式、包的格式。插件里面的东西一律不碰。
4. **仪器和被验的系统分开**。验证代码是仪器，从你仓库里的 `validation/` 来，只用提交过的；被验的系统从要验的那个提交克隆出来。
   这样同一把尺子能量新旧两个版本，比较才公平。仪器要是跟着系统一起变，新旧两版的差别里就分不清哪些来自系统、哪些来自尺子。
5. **验证用自己的一本账**，和你的 `data\` 分开，各个版本共用这一本；远端作业根目录和 FEA 归档也用验证自己的。
6. **两种跑法**（第六节）：经实验类型跑整条流程，或者照包的接口只跑一个包。

## 三、结构

    试验说明 ─┐
    适配表 ───┼─→ ①跑前对照 ─→ 设计表（存定）─→ ②拼出写全的输入 ─→ 逐行跑（经接口层）─→ ③跑后核对 ─→ 收结果 ─→ 分析 ─→ 报告
    快照 ─────┘

| 叫法 | 是什么 |
| --- | --- |
| 试验说明 | 一项试验（比如 S1）的八样：问题、因素和水平、响应量、真值和对照、重复和区组、样本量、分析、通过线。预登记 |
| 适配表 | 一个实验类型（比如 `surrogate.train`）的说明：用到哪几样输入和产物；每个设置项的单位、定义和核实等级；响应量在产物的什么地方 |
| 快照 | 预登记时从系统上拍下来的：用到的类型的三张表、内核清单里的各列、参照算例的结果。跑前对照拿现在的系统和它比 |
| 设计表 | 一项试验要跑的每一行。由试验说明和种子决定，重新生成也一模一样 |
| 一次验证 | 在一个提交上跑一组试验，编号 V0001 |

代码放在仓库的 `validation/`，属于自由的部分：系统不 import 它，它只经 `harness/port.py` 和系统打交道。
结果放在 `H:\stemlab-validation\`，不进仓库。

    validation/
      protocols/      试验说明，一项一份（R1.yaml … O7.yaml）
      adapters/       适配表，一个实验类型一份（recon.draft.yaml、fea.run.yaml、surrogate.train.yaml……）
      snapshots/      快照，一项试验一份

        component.py  组件级：照包的接口跑一个包
        stats.py      统计
        report.py     出报告
      run.py          命令行的入口

      data\  cache\  fe-archive\    验证用的账、缓存、FEA 归档，各版本共用

      V0001\

| 命令 | 做什么 |
| --- | --- |
| `python validation/run.py snapshot S1` | 预登记时拍快照 |
| `python validation/run.py plan <提交> S1` | 只做跑前对照、生成设计表、估算力，不跑 |
| `python validation/run.py run <提交> S1 S3 …` | 跑 |
| `python validation/run.py stop V0001` | 经系统把这次验证正在跑的实验停掉 |
| `python validation/run.py report V0001` | 重新出报告 |

`run.py` 自己不装系统的代码：它先在外面准备好克隆和环境变量，再起一个子进程去跑，系统的代码只在子进程里从克隆装进来。

## 四、因素分三级核

| 级 | 因素写在哪 | ① 跑前对照 | ② 写全 | ③ 跑后核对 | 现在有哪些 |
| --- | --- | --- | --- | --- | --- |
| A | 点里；包 | 内核清单里这一项的名字、单位、含义，和快照比；包按哈希认 | 契约本来就要求写全 | 数据的行带回的值和要的比，有回写的另比实际值；用了哪个包看这一轮的来历 | FEA 的全部设计和条件；用哪个内核、策略、预测器 |
| B | 设定里，产物里有机器读得出的回写 | 和快照比，再跑参照算例 | 适配表的设置项清单，每一项都明写 | 回写的值和要的比 | 代理的模型选项（degree、members、alpha）、训练的种子 |
| C | 设定里，产物里没有机器读得出的回写 | 探针 | 同 B | 靠跑前的探针 | 重建 CT 的各项、三角网边长、候选池的取法和散布 |

核的不只是因素：固定条件也一样核。固定条件被悄悄忽略，试验的条件就不是说明里写的那样了。

**探针**是阳性对照。一个 C 级的因素，跑前先拿两个差得很远的水平各跑一个小例子，看一样必定会跟着变的东西变没变。
比如候选池的取法写拉丁超立方和写随机：前者取出的设计每一维都正好分层，后者几乎不会；散布写 0.05 和 0.3，取出的点离中心的远近会差好几倍。
没变，说明这一项根本没用上，停。重建的那几项也照这个办法做，指标用产物里量得出来的东西。探针便宜（取点几秒，重建一两分钟），每次验证都先跑。

既不在点里、又没法用探针核的设定项，不许当因素，只能当固定条件，报告里写明“没核实”。

设定里的因素要升成 A 级，系统那边要做三件事：插件把设置项说出来（名字、单位、范围、默认值、定义）；核心启动时拒绝不认识的项；
把实际用的设定记进这一轮。这和你在整理的设置项、和操作台的设置表单是同一件事，等你整理完一起定。
到那时，验证代码这边只要把适配表里的设置项清单换成向系统查，别的都不用动。

## 五、三道保险每一步做什么

### ① 跑前对照

什么都不跑，只查、只比。有一条不过就停，说出是哪一条。

| 对照什么 | 怎么比 | 对不上怎么办 |
| --- | --- | --- |
| 版本 | 克隆的提交号；FROZEN 对得上；契约和核心干净；装进来的 `stemlab` 和 `plugins` 确实来自克隆；仪器（`validation/`）没有没提交的改动（只做 `plan` 和自测时不要求） | 停 |
| 环境 | 克隆里的锁文件和现在装的环境一致 | 停：先同步环境 |
| 类型的三张表 | 用到的输入、产物、结局，和快照比 | 用到的变了：停；多了没用到的：记一笔 |
| A 级因素 | 内核清单里的设计、条件、pre、labels 各列，和快照比 | 名字没了、单位变了：停；含义变了：停，请你看；多了一项条件：停（试验说明没写它取多少，系统又不许空着） |
| B、C 级因素 | 参照算例的结果和上一版比；C 级跑探针 | 参照算例变了：记一笔“这个版本的行为变了”；探针没变：停 |
| 真值和数据 | 哈希和试验说明里登记的一致；来源标明了不含病人的数据（公开的数据集、合成的、在复合骨这类模型上算出来的） | 停 |
| 算力 | 估出的 FE 次数、CPU 小时，不超过试验说明的预算 | 停 |
| 远端 | 用到 worker 的，先连一次 | 停 |

### ② 拼出写全的输入

- 点：契约要求每个点的设计和条件写全，照设计表的水平写进去。
- 设定：适配表里有一份设置项清单（每一项的键、单位、定义）。试验说明给每一项一个值，拼出来的设定每一项都明写；
  少写一项就停，验证代码不替谁补默认值。
- 验证用的导出设定是一份固定的、登记过的设定，各次验证都用这一份：`archive_root` 指向 `H:\stemlab-validation\fe-archive`，
  `build_slots` 写 2，几个超时也都写明。各次用同一份，第十节的 FE 结果重用才成立。
- 拼好的设定照样经系统登记，所以账里存的正是交给插件的那一份。

### ③ 跑后核对

每一行跑完就核，对不上的那一行作废。

- A 级：按点的哈希对齐，数据的行带回的设计和条件，和要的比；有回写的另比实际值：`h_mesh_mm` 和要的 `h_int_mm`，
  `load_x_N`、`load_y_N`、`load_z_N` 和要的 `load_N` 加两个倾角；用了哪个包，看这一轮的来历。
- B 级：产物里回写的值和要的比，数值的差在容差以内算对上。
- C 级：已经由跑前的探针核过。
- 系统给的结局也在这一步看，和试验说明里逐行写的预期比。轮的结局（done、failed、stopped、start_failed）和
  任务的结局名（trained、finished、misfit……）是两样东西，分开写、分开比。有的试验要的就是“被拒”或“放不进去”（O4、F6），
  这时候被拒是响应，不是事故；启动被拒的时候还没有轮，在启动那一步就判，不等到这一步。
- 代理的误差报告里记着每个量缺了几个预测（unmatched）、几个点给了不止一次（repeated）、几个点算不了（skipped）。
  2026-11-15 起冻结的判定看它们：哪一样不是零，那一部分的合格线就不可判（之前 100 个留出点只给回 1 个预测，合格线照样判过）。
  验证代码在这一步仍然自己核一遍，不靠系统自觉：缺了预测的那一行作废；另设一项反向试验，故意少给预测，判定必须是不可判。
- 任务按集合核：这一行该有的任务（FEA 就是每个点一个）一个不少、不多；必需的产物必须在，不是“交了才核”。
- 数值怎么比由适配表逐项定：哈希、编号、枚举和验证代码自己写进去的设定严格相等；系统算出来的数和物理量，
  用试验说明里写明依据的容差，不用一个统一的小数。
- 作废的行不进分析，报告里逐行列出原因。作废的超过试验说明写的比例（建议 5%），整项试验停下：多半是系统性的问题。

## 六、两种跑法

| | 整条流程 | 组件级 |
| --- | --- | --- |
| 怎么跑 | 经实验类型：登记输入、新建、填、启动、轮询到这一轮结束、读产物 | 照包的接口直接跑一个包：一条命令，加输入和输出两个文件夹；`job.json` 进去，`result.json` 出来 |
| 验的是 | 插件加包的整体，和你在操作台上用的一样 | 包里的算法本身 |
| 快慢 | 每个实验都有登记、启动、轮询的开销 | 快得多，适合要跑上千次的基准 |
| 用在 | R 系列、F 系列、S1、S5、O1、O4、O7 | O2、O3、O6，S7 里推理那一半 |

两种跑法都只碰固定的部分：包怎么跑、四种包的 job 和 result 长什么样，契约里都写定了。组件级也照契约，先过包的自检样本再用。
组件级不经插件，所以插件里的保护（选点前的约束检查、不同内核的数不放在一起用）不起作用；要验这些的，必须走整条流程。
用组件级的试验，每项抽几行也走一遍整条流程，两边的结果要相同（比如同一个策略包选出同样的点），否则组件级的结果不算。

整条流程里，跟被验的东西无关、又很贵的那一环，可以换成替身。比如 O1 验的是候选池的取法，要取十几万个设计；
用真内核，每个设计都要模板化一遍，太慢。换成一个只会模板化、马上答“放得进”的替身内核，验的仍然是取法。
用了替身，试验说明里要写明，结论也只说被验的那一环。

## 七、一次验证怎么跑

1. 先把要验的版本提交。克隆到 `V0001\repo`，检出那个提交。
2. 改克隆里的机器清单：远端作业根目录换成 `/home/linux-user/stemlab-validation-jobs`，备份根目录也换掉，
   操作台的求解槽数写 2。改的是克隆里的那一份，仓库里的不动（和测试搭实验室的做法一样）；改了什么记进 `campaign.json`。
   机器清单不在契约和核心里，改它不影响启动时的代码检查。
3. 起子进程：工作目录在克隆里；`STEMLAB_REPO` 指克隆，`STEMLAB_DATA`、`STEMLAB_CACHE` 指验证自己的；
   `STEMLAB_SLOTS` 明写成整台机器共用的那个文件夹（你平时没设它，就是 `%LOCALAPPDATA%\stemlab\slots`）；数值库的线程数限 4。
4. ① 跑前对照。验证用的账里如果还有上一次验证没收尾的实验，不开新的一次。
5. 生成设计表，存定（记下哈希）。
6. 一行一行地跑，一次一个实验：拼好写全的输入并登记，新建、填、启动；在这个进程里每隔几十秒轮询一次，直到这一轮结束。
   在 worker 上跑的实验，每次轮询系统都要连一次远端，所以隔一分钟看一次就够了。
   可以重试的结局（比如许可证一时不够）照试验说明重排，最多几次；“待查”的不重试，留给人看。
7. ③ 跑后核对，收结果。
8. 一项试验跑完，照预登记的分析出报告。

断了能接着跑：每一步做完先记进 `runs.jsonl`。重新起来以后不只看自己的记录，还照核心的记录对账，因为动作可能做成了、
本地还没来得及记：建了没记下编号的，按运行标识找回来；建了没启动的，补齐输入再启动；在跑的接着轮询；结束了的直接核对。
运行标识由这一次验证、试验说明、行号、第几次算出，写在实验的备注开头；两次验证跑同一份试验说明的同一行，也认不错。
卡没卡住由系统自己判：FEA 的建模、求解、后处理各有超时，训练有心跳。记录长不长不能当进展，一次求解正常跑几个小时，
中间可以一条新记录都没有。验证代码只设整行的期限（比系统自己的超时宽），过了就经系统停下，确认停住了再报。
在跑的 FE 作业是系统脱离出去的进程，验证的进程没了它们照样在跑；要真停，用 `stop`，经系统去停。

由我来跑的时候：整次验证是一个后台进程，跑完自己退出。我等它退出的通知，不另外起循环去盯。

## 八、试验说明和适配表长什么样（示意）

一份试验说明。S7 里最简单的一条：同样的数据、同样的设定，重训两次。

```yaml
id: S7a
question: 同样的数据、同样的训练设定和划分，重训两次，交出来的预测器是不是逐字节相同？
level: system                  # 整条流程，经 surrogate.train
module: surrogate.train
inputs:
  data: [{hash: "<旧库 v0.14 转来的那份数据的哈希>"}]     # 外面拿来的东西按哈希认
settings:                      # 适配表里设置项清单的每一项都要写，少一项就停
  setting:
    seed: 1
    targets: [rot_first_deg, f1_p95_um]
    level: 0.95
    model: {name: ridge, degree: 2, members: 20, alphas: [0.01, 0.1, 1, 10]}
    # …清单里其余的项
  split: {…}
factors: []                    # 没有因素，只有重复
design: {kind: repeat, times: 2}
expect: {round: done, outcomes: {"*": trained}}   # 轮的结局和任务的结局名分开写；要的是“启动被拒”写 {refused: true}
deadline_s: 3600               # 一行最多跑多久，要比系统自己的超时宽
responses: [predictor_hash]
analysis: analysis/surrogate.py:same_bytes
lines:
  - {name: same_bytes, op: "==", value: true}
invalid_max: 0                 # 作废的行最多占多少
budget: {fe_runs: 0, cpu_hours: 0.5, worker: true}
```

一张适配表：

```yaml
type: surrogate.train
uses:                          # 跑前对照：和快照比
  inputs: [data, setting, split]
  outputs: [predictor, report]
settings:                      # 设置项清单
  setting:
    seed:          {unit: "1", meaning: 随机种子,         grade: B, echo: "report: training.seed"}
    model.name:    {unit: "-", meaning: 用哪个模型,       grade: C, probe: {levels: [ridge, pod], watch: "预测器包里的推理代码"}}
    model.degree:  {unit: "1", meaning: 多项式的次数,     grade: B, echo: "report: training.model.degree"}
    model.members: {unit: "1", meaning: 集成里有几个成员, grade: B, echo: "report: training.model.members"}
    # …其余的项
responses:
  predictor_hash: "predictor: 登记时的哈希"
  rmse_dex:       "report: 留出点上的均方根误差"
reference:                     # 参照算例：每个版本先跑一遍，和上一版比（比数，不比哈希：打包的代码一改哈希就变）
  - {name: small-ridge, data: "<一份小数据的哈希>", compare: [rmse_dex], tolerance: 1e-9}
```

YAML 能写中文注释，方便你看、方便你改。读进来以后，按字段一项一项核：多一项、少一项、类型不对，都停。

## 九、系统改了以后

| 改了什么 | 验证代码怎么反应 | 要你做的 |
| --- | --- | --- |
| 插件里自由的代码（算法、模型、界面） | 照样跑。参照算例和上一版比出差别，报告里写“这个版本的行为变了” | 没有。要比新旧两版，同一份试验说明在两个提交上各跑一遍 |
| 设置项改了名 | B 级：回写对不上，停；C 级：探针没变，停 | 改适配表里那一行，重拍快照 |
| 设置项挪了地方（比如挪成单独一样输入） | 三张表变了，跑前对照停 | 改适配表 |
| 默认值变了 | 不受影响：每一项都明写 | 没有 |
| 名字没变、含义变了 | 点里的：内核清单的含义和快照对不上，停，请你看。设定里的：现在发现不了，只能靠参照算例；要等插件把设置项说出来 | 看一眼，认可就重拍快照 |
| 新增了一项 | 点里的：停，试验说明没写它取多少。设定里的：现在只能靠参照算例发现 | 试验说明补上它的值 |
| 插件的检查改严了 | 启动被拒，停，说出原因 | 看是试验说明的问题还是系统的问题 |
| 实验类型的三张表变了 | 用到的变了，停 | 改适配表 |
| 换了内核 | 内核按哈希认，换了就和试验说明对不上，停；列变了，快照那一条也会停。系统本来也不许不同内核算的数放在一起用 | 新内核当作一个新模块（新的快照），或者把内核当因素 |
| 新插件，新的模块 | 现有的试验不受影响 | 写它的适配表和试验说明；产物如果是十六种之一，读法通用 |
| 替代现有模块的插件 | 把“用哪个模块”当因素，同一份试验说明就成了 A/B 对比 | 写它的适配表 |
| 契约或核心改了 | 跑前对照停在“版本”那一条；接口层和通用读法可能要跟着改 | 这本来就是固定的部分，要你点头 |
| 验证代码自己改了 | 设计表或分析的哈希变了，就算一份新的试验说明，报告里写明偏离了预登记 | 看偏离的理由 |

## 十、结果怎么和版本绑在一起，贵的结果怎么重用

- 预登记留两处痕：试验说明和快照提交进仓库；每次验证开始时，再把它们登记进验证用的账（登记有时间、有哈希链），
  时间一定早于这次验证的任何一轮。
- 试验说明的身份是四样合起来的哈希：它自己、它用的适配表、快照、它点名的分析代码。改了其中哪一样，都算一份新的。
- 每个数都带着：试验说明的身份、被验系统的提交号和 FROZEN、插件的哈希（取自这一轮的来历）、内核是哪一个（made_by）、环境锁、仪器的版本。
- 不同版本的结果不放进同一次分析，除非“版本”本身就是因素（回归比较：同一份试验说明，新旧两个提交各跑一遍，按事先定好的等价界比）。
- 贵的 FE 结果可以跨版本重用，但只限系统自己会认作同一个作业的：点、骨模型、内核、导出设定、插件的冻结文件，五样都没变
  （系统给 FE 作业算输入指纹，用的就是这五样，验证代码不自己另立标准），再加上推导量定义也没变（数据里推导出的那几列靠它）。
  有一样变了，就重算。

## 十一、算力和安全

- 同一时间只有一次验证在跑（`H:\stemlab-validation\` 下有一把锁）。
- 一次验证里一次只跑一个实验。一个实验里 FE 的并发走整台机器共用的槽：建模的槽数写在导出设定里（`build_slots` 写 2），
  求解的槽数写在机器清单里（克隆里写 2）。验证和你自己的实验抢同一组槽，加起来不超过你平时的上限。
- Abaqus 的许可证也是共用的。你自己在算的时候，验证的作业可能因为许可证不够得到“可以重试”的结局，照试验说明重排就是了。
- 验证代码自己的计算（体模、统计、组件级的基准）在同一个进程里，数值库的线程数限 4。
- 每项试验写明 FE 次数和 CPU 小时的上限：跑前估，跑中数，超了就停。
- 远端用验证自己的作业根目录，一次一个作业。
- 不碰你的账：`STEMLAB_DATA` 指向仓库的 `data\` 就拒绝起来。不碰病人的数据：只收试验说明里列明、标明不含病人数据的来源，标不出来的不收。

## 十二、验证代码自己怎么验

仪器先校准，再拿去量。下面这些都不用 FE、不用远端，放在 `tests_free/validation/`，跟着检查一起跑。

- 统计：每个函数对照已知答案，比如 Bland–Altman 原文的例子、ICC 的 Shrout 和 Fleiss 的例子、GCI 的 Celik 2008 的例子。
- 三道保险：拿测试插件故意造坏：设置项改名、插件悄悄忽略一项、一个因素根本没用上、三张表改了、内核多了一项条件。
  每一种都要被拦住，而且要停在该停的那一步。
- 断点续跑：跑到一半结束进程，续上以后的结果要和一口气跑完的逐字节相同。
- 组件级和整条流程对得上：同一个策略包，两种跑法选出同样的点。
- 依赖：一条测试守着，验证代码只 import 系统的固定部分，系统也不 import 验证代码。

## 十三、先搭哪些

1. **骨架和自测**：接口层，一次验证（克隆、隔开），跑前对照，设计表（先做重复、逐行列出、全因子三种），拼输入，逐行跑，跑后核对，
   按种类读产物，出报告；再加上第十二节的自测。用测试插件跑通，不用 FE、不用远端。
2. **阶段 A 里最便宜、又最能说明问题的几项**：S7（重训可重复，用旧库 v0.14 转来的数据，要连 worker）、S3 和 S4
   （同一份数据上的重复划分和校准）、O5（选点重放）、O1（取样核验，先做替身内核）。
3. **真值**：R1 的数字体模，O2 的测试函数（组件级）。F1 的解析解要另做一个专门的“核验内核”包，正好是第九节里“新模块”的走法：
   新包，加适配表，加试验说明。
4. **阶段 B、C**，照 [验证实验.md](验证实验.md) 第七节的顺序：前一阶段没过，后一阶段不开。

## 十四、要你定的

1. **验证代码放在哪**：放在这个仓库的 `validation/`（我建议这样：一个仓库好管，第二节第 4 条已经让仪器和系统分开装）；
   或者单独建一个仓库（和系统彻底分开，但要多管一个仓库）。
2. **试验说明用 YAML 还是 JSON**：我建议 YAML，能写中文注释。
3. **要验的版本先提交**。现在没提交的改动里，made_by 那 14 处固定部分的改动还没定，提交之前要先定下来。
4. **系统那边要不要补上第四节说的三件事**（插件说出设置项、核心拒绝不认识的项、记下实际用的设定）：
   和你整理设置项、和操作台的设置表单是同一件事，等你整理完一起定。不补，验证代码照样能跑，只是设定里的因素停在 B、C 级。
