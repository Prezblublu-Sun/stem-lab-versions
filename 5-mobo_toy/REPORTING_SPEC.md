## 2. 每份报告的统一结构

`report.py` 按下面的固定结构生成报告，内容来源写在右列。

| 节 | 内容 | 来源 |
|---|---|---|
| 页眉 | 报告号、阶段、生成时间、spec.yaml 哈希、**总判定**（PASS / FAIL / INCOMPLETE） | 自动 |
| 0 结论摘要 | 三到五句：本阶段结论、关键数字、是否可进入下一阶段 | `text/summary.md`（必填） |
| 1 使用情境与问题 | 使用情境、要回答的问题、**不回答**的问题、依据规范 | spec.yaml |
| 2 输入与版本 | config.yaml 与 spec.yaml 哈希；每个生成脚本与作图模块的哈希；软件包版本；Abaqus 版本、runs.csv 行范围、种子等 | 自动 + `inputs.json` |
| 3 方法 | 按 Erdemir 2012 对应类目简述；写明与上一阶段相比改了什么 | `text/methods.md`（必填） |
| 4 结果 | 必备图按 spec 顺序排列，未登记的附加图放后面；必备表 | `figures/`、`tables/` |
| 5 验收 | 每个验收项的判据、门槛、实测、状态、原因与处置 | spec.yaml + `acceptance.json` |
| 6 局限与下一阶段输入 | 通用局限 + 本阶段局限 + 交给下一阶段的东西 | spec.yaml + `text/limitations.md` |
| 附录 A 溯源 | 每张图表的数据哈希、作图函数、生成脚本哈希、是否合成、数据来源 | 自动 |
| 附录 B 缺项 | 规范要求但没交的图、表、验收、文字；数据哈希不符 | 自动 |

**缺项不阻止生成**：报告照样出，但首页标"草稿"，总判定为 INCOMPLETE，`report.py` 退出码为 2。一个阶段只有在其报告总判定为 PASS（或 FAIL 项都写了处置并经用户同意）后才进入下一阶段。

## 3. 作图与制表规范

**颜色与标记（`plotstyle.py` 固定，全项目不改）**

| 对象 | 规定 |
|---|---|
| Dorr A / B / C | Okabe–Ito 色盲友好色：A 蓝 `#0072B2`、B 蓝绿 `#009E73`、C 朱红 `#D55E00`；标记 A 圆、B 方、C 三角，灰度打印也能分 |
| 方法 | 用线型分：qNEHVI 实线（分型色）、Sobol 虚线灰 `#7F7F7F`、参考前沿黑实线 |
| 多种子 | 单个种子细线半透明，中位或均值粗线；误差带写明是 ± 2 SE 还是四分位 |
| 失败等级 | OK 黑、L1 橙、L2 紫、L3 天蓝、L4 朱红、L5 黄（CLAUDE.md §10） |
| 门槛线 | 黑色点线并标数值，如 50 µm、150 µm、HV 比 0.9、壁厚 1.0 mm |

**尺寸与格式**：宽度按 Elsevier 栏宽 90 mm（单栏）、140 mm（1.5 栏）、190 mm（双栏）；印刷尺寸下正文字号 8 pt，最小 6.5 pt。每张图同时存 PNG（300 dpi）与 SVG（文字可编辑）。多面板图左上角标 (a)(b)(c)。

**文字**：图内文字用英文，方便直接进论文和导师汇报；报告正文用中文。轴标签一律带单位，用 `plotstyle.LABEL` 里的标准写法（例如 `Micromotion P95 (µm)`、`Gruen 7 SED loss (%)`、`HV / HV_ref (–)`）。

**图题与图注**：图题写**结论句**（例如"Dorr B 上 qNEHVI 在 36 次 FE 内达到参考前沿 HV 的 90%"），放在报告图注里，不画进图内；图注说明图里有什么、样本量、误差棒含义、怎么读。

**坐标**：跨分型比较的图共用坐标范围（`plotstyle.shared_limits`）；跨度超过两个数量级的量用对数轴并在标签里写明。

**表格**：数值统一三位有效数字；单位写在表注或列名里；超过 60 行的表在报告里只显示前 60 行，全表在 CSV。

**合成数据**：演示或占位数据必须 `synthetic=True`。图上自动加"SYNTHETIC"水印，报告首页加横幅，溯源附录标"是"。合成数据永远不能出现在 R0–R7 的正式判定里。

## 4. 溯源与文件规范

**目录**

```
reports/
  spec.yaml                       报告登记表（唯一真源）
  checklists/erdemir2012_checklist.csv
  R2_fe_verification/             每份报告一个目录，名字见 spec.yaml 的 dir
    figures/R2-F03.{png,svg,csv,json}
    tables/R2-T02.{csv,json}
    text/{summary,methods,limitations}.md
    acceptance.json  inputs.json
    R2_report.{md,html,pdf}
    history/R2_report_<yyyymmdd-hhmm>.pdf
```

**编号**：图 `Rk-Fnn`、表 `Rk-Tnn`、验收 `Rk-An`，一经登记不改号；报告内另按出现顺序编"图 1、图 2"，并在括号里给出固定编号。

**图只由数据画出**：生成脚本先把数据写成 CSV，再由一个模块顶层的作图函数 `plot_fn(csv_path)` 读 CSV 出图（`plotstyle.publish_figure` 强制这个顺序）。meta JSON 记录：结论句图题、图注、单位、数据来源（runs.csv 行范围、design_id 范围）、CSV 的 sha256、作图函数位置与其模块哈希、生成脚本与其哈希、config.yaml 与 spec.yaml 哈希、生成时间、Python 与 matplotlib 版本、是否合成。`python report.py --replot R2-F03` 只凭 CSV 重画；CSV 哈希不符时拒绝重画，报告缺项附录也会列出。

**版本**：项目目录目前不是 git 仓库，版本靠文件哈希追踪；每次生成 PDF 自动存一份带时间戳的副本到 `history/`（Erdemir 2020 规则 5）。

**运行记录**：FE 结果一律来自 `results/runs.csv`（CLAUDE.md §9，一行一设计、成败都记），报告里的数据来源写 runs.csv 行范围与 design_id 范围。

## 5. 验收表规范

| 状态 | 含义 | 要求 |
|---|---|---|
| PASS | 达到门槛 | 写实测值 |
| FAIL | 未达门槛 | 必须写原因与处置（改什么、是否重跑、是否需要用户决定） |
| NA | 本次不适用 | 必须写理由 |
| PENDING | 还没提交结果 | 由 report.py 自动标出 |

总判定：全部 PASS（或写明理由的 NA）为 PASS；有 FAIL 为 FAIL；所有 FAIL 项的处置都已获用户同意（验收项带 approved 日期）为 FAIL-APPROVED，可进入下一阶段；有 PENDING、缺图表或数据哈希不符为 INCOMPLETE。验收门槛写在 spec.yaml，改门槛要在报告第 3 节说明理由。
