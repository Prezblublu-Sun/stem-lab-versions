# ADR-007 b28 的判据在批准后、喂料前按审查修订

**定于** 2026-11-08，实验会话。等用户重新批准判据后生效。

## 背景
用户先批准了 b28 的 17 行（"批准 17 行"），批准时判据只写在 proposal.md 里，gates.py 随后按提议写成，sha256 bbe5bf08…记进 approval.md。之后按 `experiments/README.md` 第 1b 步做第二模型审查（Claude Sonnet 5.5），结论是"改完再批"：G41 在有行失败或缺数据时会给出错误的不过，G44 会静默取端点，h 1.4 的条件行没有判据用它。

## 决定
在看到任何 b28 的 FE 结果之前修订 gates.py：G41、G42 在数据不全时判不适用；G44 先查范围；新增 G45（赢家的 h 1.4 网格敏感度）；写明 N3、CREF 的来源。阈值和两条路线都没有改。修订后的 sha256 是 9215f08a…，用户重新批准后写进 approval.md。

## 过程中的问题
gates.py 是用整文件重写改的。守护钩子 `ops/guard_pretooluse.py` 只拦 Edit 和 Bash 的写法，没有拦整文件写入，所以这次修订没有被挡住；随后一次 Edit 被它拦下。写这批的模型在发现后停手，没有再改 gates.py，并向用户说明。钩子的这个缺口要补，另提。

## 被否的方案
- 按原判据喂料：审查指出的 R1 会在关键行失败时给出错误的结论，不能接受。
- 删掉 h 1.4 的条件行：可以省约 3.75 槽时，但用户关心网格收敛，留着并用 G45 消费它更有用。

## 后果
- b28 的批准分两次：行（11-07、11-08）和修订后的判据（待定）。
- 以后的批次按 README 的顺序先审查、后批准，避免再出现这种情况。
